# 实时决策讲解与可选健康档案设计

日期：2026-09-02
状态：已获交互方向确认，待文档复核

## 1. 目标

本变更解决两个直接影响前端使用的问题：

1. 推荐过程中不再只显示“正在分析”或阶段名称，而是持续输出用户可读的判断、比较、修正和取舍。
2. 固定健康档案改为可选加载。用户可以加载零份、一份或多份已有档案；不加载档案时，仍可直接在聊天中用自然语言描述健康情况。

最终菜单仍必须经过现有 RAG、B4 健康审核、菜单规划和最终校验后才能提交。实时讲解是解释层，不得改变健康规则或绕过确定性校验。

## 2. 非目标

- 不创建健康信息填写表单、档案编辑器或新数据库。
- 不上传、修改或写回现有 50 份固定档案。
- 不直接输出模型内部原始思维链、隐藏提示词或工具私有上下文。
- 不在健康校验完成前声称某道菜“安全”或承诺最终菜单。
- 不重构现有 RAG、B4、菜单规划和 Redis 会话主链。

## 3. 当前行为与问题

### 3.1 流式展示

后端已有 SSE，并会发布 `request_accepted`、`analysis_ready`、`answer_ready` 和 `result_committed` 等事件。前端当前只把 `analysis_ready` 显示为阶段列表，且未订阅已经存在的 `answer_started`。正式正文要等 `answer_ready` 才一次性出现，因此用户看到的是进度播报，而不是边分析边讲解。

### 3.2 健康档案

公共请求当前强制至少包含一名参与者。`p1..p50` 会在服务端确定性映射到固定 `user_id 1..50`，所以前端“添加匿名成员”实际上会隐式加载固定档案。接口不能表达“本轮不加载任何固定档案”。

聊天中的疾病、过敏和禁忌已经可以通过 QueryNormalizer 转成会话临时约束，但该链路要求临时约束归属于一个请求参与者。

## 4. 方案选择

### 4.1 采用：基于真实 Artifact 的千问讲解流

在结构化结果已经产生的检查点，把允许公开的事实交给千问，生成简短、自然、第一人称的用户可读讲解，并将模型返回的文本增量通过 SSE 立即推送。讲解必须基于实际 QueryPlan、检索候选、健康审核结果和最终菜单，不允许自由预测尚未产生的结果。

选择该方案的原因：它能输出真正的判断和取舍，同时保持与真实链路一致；比固定模板自然，又比请求开始时自由生成整段推理可靠。

### 4.2 不采用：固定模板

固定模板速度快、成本低，但结果仍接近“已完成检索”“已完成审核”的进度播报，不满足本次交互目标。

### 4.3 不采用：请求开始即自由生成长推理

在检索和健康审核结果出现前持续自由生成容易产生错误假设，并可能与后续真实结果矛盾，因此不进入实现。

## 5. 用户交互

### 5.1 健康档案选择

- 页面首次打开时默认不加载固定健康档案。
- 顶部原“匿名成员”区域改为“加载健康档案”。
- 点击后打开可搜索的多选列表，选项使用 `档案 1` 至 `档案 50`，并展示性别、年龄和已派生约束数量，帮助用户识别测试档案。
- 选中的档案显示为可移除的标签；允许零选、一选或多选。
- 不提供任何健康字段填写表单。
- 选择变化后沿用现有规则：参与者组合变化即创建新会话，避免不同档案组合共享旧约束和菜单。

### 5.2 不加载档案

- 前端在零选择时仍允许发送消息。
- 服务端在请求内部创建一个 `guest` 参与者，但不为其加载固定 `user_id` 或永久健康约束。
- 用户没有输入健康信息时，`guest` 仅代表普通用餐人，健康审核仍执行，但约束集合为空。
- 用户在聊天中输入“我高血压”“花生过敏”“不能吃辣”等内容时，语义理解结果归属于 `guest`，经过现有 B2 临时信号验证后写入 C4 会话约束，再由 B4 消费。

### 5.3 多档案与临时健康信息

- 多份档案同时加载时，现有逐参与者健康审核保持不变，最终菜单必须对所有选中档案安全。
- 只有一份档案时，本轮自然语言健康信息可以直接归属于该参与者。
- 多份档案时，明确指向某个档案或“所有人”的健康信息按原话归属；无法确定归属的健康信息进入现有澄清终态，不擅自套用给任意参与者。

### 5.4 实时讲解

助手气泡从第一段可用讲解开始持续增长，用户看到的是连续文字，而不是阶段列表。例如可以包含：

- 对模糊表达的解释以及没有直接排除某类食材的原因；
- 候选菜之间的比较，以及某道菜为何因为真实食材或健康约束被排除；
- 前一判断在获得新证据后如何修正；
- 最终菜单在安全、口味、数量和时间之间的取舍。

正式答案与菜单放在同一助手气泡的“最终建议”部分。现有阶段列表不再作为主界面展示，可保留在开发调试状态中。

## 6. 后端设计

### 6.1 健康档案选项目录

新增只读接口：

`GET /v1/health-profile-options`

响应示例：

```json
{
  "build_id": "current-ready-build",
  "profiles": [
    {
      "participant_ref": "p1",
      "label": "档案 1",
      "gender": "女",
      "age": 42,
      "constraint_count": 2
    }
  ]
}
```

数据必须通过现有 B2 `UserHealthProfileService` 从 H07 ready build 读取，不从前端静态文件或旧数据目录读取。接口不返回姓名、具体疾病、检查指标、过敏详情或内部 `user_id`。

### 6.2 请求参与者

- `POST /v1/sessions` 和 `POST /v1/recommendation-requests` 接受空 `participants` 数组。
- 非空数组仍只接受 `p1..p50`，并保持重复、越界和 `user_id` 注入校验。
- 空数组在 D1 内部解析为 `{"participant_ref": "guest", "user_id": null}`；`guest` 不能由公共请求显式伪造。
- C3/C4 的参与者映射类型扩展为 `dict[str, int | None]`。永久档案加载、档案口味子查询和 B2 永久约束派生必须跳过 `None`，但仍保留 `guest` 作为临时约束和健康审核的归属主体。

### 6.3 临时健康约束

- QueryNormalizer 在零档案场景使用 `guest` 作为唯一 `participant_ref`，所以现有单人健康语义可以确定归属。
- `_handle_query_plan_exclusions` 按参与者键是否存在做归属校验，不要求该键必须拥有固定 `user_id`。
- `_get_health_constraints`、候选健康审核和最终健康校验分别合并：固定档案约束（若有）与 C4 会话临时约束。
- 对 `guest` 只读取 C4 临时约束，不调用 `derive_constraints(None, ...)`。
- B2 临时信号验证与食材标准化继续 fail-closed；无法映射的疾病、过敏或禁忌进入澄清，不静默忽略。

### 6.4 讲解生成器

新增单一职责的 `ReasoningNarrator`：

- 依赖现有千问 OpenAI 兼容 API 配置，不新增模型或供应商。
- 输入是经过白名单投影的结构化事实快照，不接受工具对象、连接信息、完整健康档案或隐藏提示词。
- 输出为面向用户的短段落，不输出步骤标题，不伪造数量，不提前宣称安全。
- 每个检查点最多生成一个短段落，控制额外调用和延迟。

三个检查点：

1. QueryPlan 产生后：解释用户表达、关键条件和当前仍保留的不确定性。
2. RAG 与 B4 候选审核后：比较真实候选、说明保留/排除与必要的判断修正。
3. 最终菜单校验后：解释组合取舍，并衔接正式答案。

讲解不是健康审查事实来源。模型文本与 Artifact 冲突时，以 Artifact 为准；服务端不得把讲解文本反向写入约束或菜单。

### 6.5 SSE 事件

新增事件：

- `reasoning_delta`：讲解文本增量，字段为 `segment_id`、`sequence`、`delta`。
- `reasoning_completed`：一个讲解段落完成，字段为 `segment_id`。
- `answer_delta`：最终答案文本增量，字段为 `sequence`、`delta`。

保留现有 `answer_ready` 作为完整答案权威事件，保留 `result_committed` 作为菜单真正提交成功的终态事件。SSE 事件继续使用稳定事件 ID，重连后由前端按事件 ID 和序号去重。

如果现有回答生成路径只能先得到完整文本，服务端可按短文本块发布 `answer_delta`，但 `answer_ready` 中的最终文本必须与所有增量拼接结果完全一致。

### 6.6 错误处理

- 千问讲解调用失败、超时或返回空文本时，不中断推荐主链。
- 失败检查点发布一段基于事实快照的简短解释作为 fallback，不发布模型错误堆栈。
- QueryNormalizer、RAG、B4、菜单规划或最终提交失败仍沿用现有 fail-closed 终态。
- 在最终校验前的讲解使用“候选”“倾向”“还需验证”等措辞；只有 `result_committed` 后才能显示“菜单已生成”。

## 7. 前端设计

### 7.1 状态

新增：

- `profileOptions`：可加载档案选项。
- `selectedProfileRefs`：已选档案，默认空数组。
- `reasoningText`：按 SSE 增量拼接的讲解。
- `answerText`：按最终答案增量拼接的正式回答。
- 每个 segment/sequence 的去重集合，处理 SSE 重连。

`canSend` 不再依赖至少一名参与者，只依赖消息非空且当前无请求运行。

### 7.2 组件

- 将 `ParticipantContext` 改为档案加载选择器，保留轻量标签式展示。
- `ChatPanel` 在同一个助手气泡中依次渲染 `reasoningText` 和 `answerText`。
- 流式过程中显示文本光标，但不显示“正在分析……”作为主要内容。
- `analysis_ready` 仍可进入 store 供调试和测试，不再作为用户主视图的阶段清单。

### 7.3 会话

- `selectedProfileRefs=[]` 具有稳定空指纹，可创建并复用无固定档案会话。
- 发布时升级前端本地存储键版本，不继承旧版自动创建的 `p1` 匿名槽位；升级后的首次打开必须是零档案选择。
- 档案选择发生变化时，结束当前 SSE、创建新会话并清空不应跨组合继承的菜单展示。
- 聊天自然语言形成的临时健康约束仍按现有 C4/Redis 会话范围保存。

## 8. 测试与验收

### 8.1 后端

- 档案选项目录只返回允许字段，数量为 50，build_id 与 H07 ready build 一致。
- 空参与者请求通过校验，并在内部形成 `guest`，公共响应不暴露内部映射。
- `guest` 无健康描述时具有零永久约束且可以完成推荐。
- `guest` 输入明确过敏/禁忌时形成临时约束，并在候选审核和最终校验中生效。
- 多档案继续逐参与者审核；含 `None` 的映射不会调用 B2 固定档案派生。
- `reasoning_delta` 顺序、去重、重连续传和失败 fallback 有契约测试。
- `answer_delta` 拼接文本与 `answer_ready.text` 完全一致。

### 8.2 前端

- 默认零档案时发送按钮可用。
- 档案目录可加载、搜索、多选和移除。
- 请求载荷对零选择发送空数组，对已选择发送对应 `participant_ref`。
- `reasoning_delta` 被连续追加到同一助手气泡，重复事件和重复 sequence 不重复显示。
- `answer_delta` 与讲解分区展示，`result_committed` 前不显示提交成功。
- SSE 失败降级轮询后，最终完整答案仍可由 `result_summary` 恢复。

### 8.3 场景验收

至少覆盖：

1. 不加载档案、只说口味偏好。
2. 不加载档案，在聊天中说明明确过敏或疾病。
3. 加载一份档案，不额外输入健康信息。
4. 加载多份档案，验证菜单对所有人安全。
5. 多档案下输入归属不明确的健康信息，得到澄清而不是错误套用。
6. 千问讲解调用失败，但主推荐仍完成并提供事实型 fallback。

## 9. 完成标准

- 用户无需选择档案即可发起并完成推荐。
- 用户无需填写表单即可通过聊天提供健康信息，并进入现有临时约束闭环。
- 前端在最终答案前持续展示至少两段基于真实结果的自然决策讲解，而不是阶段名称。
- 最终答案和菜单仍以 B4 最终校验及原子提交结果为准。
- 当前 H07 固定档案、Qdrant、Redis 数据无需重建或迁移。
