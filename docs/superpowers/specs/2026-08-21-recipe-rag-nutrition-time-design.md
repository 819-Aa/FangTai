# 菜品语义 RAG、原始营养与任务图时长重建设计

- 状态：已批准，待书面复核
- 日期：2026-08-21
- 适用项目：`program_v2`
- 固定源数据：`data/raw/recipes_sample_2000.csv`

## 1. 目标

本设计同时解决四个相互关联、但权威边界必须分离的问题：

1. RAG 能正确理解口语化请求，并按早餐、午餐、晚餐、老人、儿童、口味和菜品类型等结构化条件筛选菜品；
2. 原始 `label` 和经审核补全的菜品画像完整进入向量文本与 Qdrant payload；
3. 营养按菜谱原始可食投料计算，不引入烹饪得率、营养保留率、份数或个人摄入量；
4. 每个真实原子步骤具有一个单点时长，并通过依赖图、厨师和设备资源约束计算单菜与菜单预计完工时间。

最终系统必须保持以下职责边界：

```text
在线语义重写
→ C1/RAG 菜品候选召回与菜品标签筛选
→ B4 健康过滤
→ B5 预计时间过滤 + B6 营养目标判断/排序
→ C2 菜单组合
→ B4 最终健康复核
```

RAG 不负责健康结论、营养计算或时间计算；B4 不使用步骤时长或计算后的营养值作健康关系事实；B5/B6 只消费 RAG 和 B4 之后的候选。

## 2. 非目标

本次不做以下工作：

- 不计算烹饪得率、营养保留率、成品重量、每份营养或个人实际摄入量；
- 不在线调用模型生成食材营养数值或步骤时长；
- 不将菜品的 `老人`、`低钠`、`控糖` 等标签当成健康安全结论；
- 不为每个用户建立厨房设备画像；
- 不构建完整的物料状态仿真或商业厨房排班系统；
- 不把 `datas` 的菜品、数量或营养结果整体迁入 V2；
- 不在正式运行数据中保留逐项置信度、来源 URL 或模型解释。

## 3. 权威数据、构建身份与发布边界

### 3.1 数据权威

`program_v2/data/raw/recipes_sample_2000.csv` 是菜谱事实的唯一固定源。编码、行数、文件大小和 SHA-256 继续由现有 `SourceManifest` 校验，原文件只读。

`datas` 仅可承担三种角色：

- 提供候选标签、候选克重和候选营养映射；
- 暴露旧处理中的异常和反例；
- 在人工审核时提供对照。

任何 `datas` 候选在进入正式 V2 产物前，都必须重新以 V2 的 `recipe_id`、源行散列、食材身份、食材状态和单位语义完成验证。禁止按菜名近似匹配后直接复制。

### 3.2 构建与发布

所有派生产物在独立 staging build 中生成，并携带同一 `build_id`、`source_manifest_hash`、Schema 版本、行数和文件 SHA-256。改变语义的产物提升主版本：

- `query_plan`：`2.0.0`
- `rag_documents`：`2.0.0`
- `nutrition_features`：`2.0.0`
- `step_tasks`：`2.0.0`

MySQL 与 Qdrant 只能从同一个已通过质量门禁的 BuildManifest 初始化。任何阶段失败时，不切换 ready build，不覆盖当前可用构建。

## 4. 在线语义识别与 RAG

### 4.1 语义重写模型

RAG 前增加一个专用的在线语义识别与查询重写步骤。实现复用项目现有 LLM 客户端和供应商配置，但使用独立的模型配置键、Prompt 版本和结构化响应 Schema；不把模型或供应商硬编码到业务逻辑。

模型输入包括：

- 当前用户原话；
- 上一轮已确认的 `QueryPlan`，用于解析“换几个清淡点的”等省略表达；
- 受控标签词表和字段说明。

模型一次输出：

```text
retrieval_query
meal_types[]
population_tags[]
dish_types[]
taste_tags[]
cuisine_tags[]
scenario_tags[]
include_ingredients[]
exclude_ingredients[]
health_constraints[]
nutrition_goal_codes[]
max_time_minutes | null
dish_count | null
```

模型只做语义识别和检索重写，不生成菜名、不作健康结论、不补写用户未表达的硬约束。否定词、餐次、排除食材和时间限制必须进入结构化字段，不能只隐藏在 `retrieval_query` 中。

输出通过封闭枚举、类型、数值范围、否定一致性和字段间规则校验。校验失败时最多重试两次；仍失败则使用原始查询和确定性解析结果，不让一次模型故障中断推荐链路。原始查询始终保留用于审计和回退，向量查询使用审核通过的 `retrieval_query`。

### 4.2 RAG 文档

每个 eligible 菜品生成一条 RAG 文档。`searchable_text` 由以下字段组成：

- 菜名；
- 标准食材显示名；
- 全部原始 `label`；
- 经审核补全的结构化 facets。

步骤全文不进入检索文本，避免设备、温度和叙述噪声干扰菜品语义。步骤摘要可作为非检索展示字段存在。

Qdrant payload 至少包含：

```text
recipe_id
name
label_tags[]
meal_tags[]
population_tags[]
dish_type_tags[]
taste_tags[]
cuisine_tags[]
scenario_tags[]
ingredient_ids[]
ingredient_names[]
catalog_eligibility
build_id
source_row_sha256
```

计算后的营养、步骤时长、用户画像、B4 关系命中和 `PASS/EXCLUDE` 结论不得进入 RAG 文档或 payload。

### 4.3 标签补全与过滤语义

原始标签保持不可变并全部投影到 `label_tags`。缺失的餐次、菜品类型、口味、菜系、烹饪方式和质地由离线模型生成候选，再由第二个独立校验步骤结合菜名、食材和步骤核对。

人群、健康功效和营养宣称属于敏感标签：只保留原始标签或通过明确证据验证的候选，不从零生成健康结论。

过滤规则固定为：

- 同一字段多个值使用 OR；
- 不同字段之间使用 AND；
- 排除条件使用 `must_not`；
- 明确餐次使用 payload 硬过滤；
- 无结果时不得静默移除餐次、人群或排除食材条件。

“推荐老人吃的晚餐”因此同时使用 `meal_tags=晚餐` 和 `population_tags=老人` 进行候选筛选，之后仍必须进入 B4/B6。

## 5. 食材画像与数量标准化

### 5.1 食材出现记录

每条菜谱食材出现记录至少包含：

```text
occurrence_id
recipe_id
ingredient_id
display_name
raw_text
food_state
condition_type: required | optional | one_of
choice_group_id | null
is_default_choice
is_process_material
standardized_quantity_g | null
edible_fraction | null
nutrition_included
```

`food_state` 必须区分原料实际加入菜谱时的状态，例如生、熟、干、泡发、水发、罐装、去皮、去骨和净肉。营养匹配使用加入时状态，不把所有食材强制映射成生鲜状态。

### 5.2 条件食材

- `optional`：保留在菜品画像和健康过滤输入中，默认不计入基础营养；
- `one_of`：保留全部候选，但只有一个默认项进入营养和健康计算；
- 不得把同组备选项相加。

当前已确认的默认项为：

| 菜品 | 备选组 | 默认项 |
|---|---|---|
| 南瓜螃蟹馒头 | 蜜豆 / 芝麻 | 蜜豆 |
| 豌豆荚馒头 | 菠菜粉 / 菠菜汁 | 菠菜粉 |
| 红酒烩牛肉 | 牛肩肉 / 牛腩 | 牛肩肉 |
| 水晶白菜蒸饺 | 菠菜汁 / 食用绿色素 | 食用绿色素 |
| 秘制叉烧 | 梅花肉 / 五花肉 | 梅花肉 |
| 秘制叉烧 | 红糟 / 红腐乳汁 | 红腐乳汁 |
| 浓香核桃派 | 葡萄干 / 蔓越莓干 | 葡萄干 |
| 洋葱牛肉包子 | 凉白开水 / 花椒水 | 凉白开水，并保留花椒粉 |

步骤中明确加入、但配料表遗漏的食材由离线补全流程生成食材候选。步骤已给出数量时使用确定性解析；没有数量时生成单点克重候选并进入人工审核。清洗水、焯水、泡发水、蒸制垫片、废弃腌料和其他不进入成品的过程材料不参与营养；实际留在菜中的水、油和调味料参与计算。

### 5.3 数量规则

正式营养计算单位统一为克：

1. 明确 `g/克/kg/千克/斤/两` 按确定性规则换算；
2. 明确范围取中点，例如 `30-40g → 35g`；
3. 明确约数保留给定数值，例如 `约100g → 100g`；
4. 明确毫升按已审核密度换算为克；
5. `个、片、勺、杯、碗` 按已审核单位重量换算；
6. `适量、少许、若干、几滴` 和无数量食材由模型结合整道菜上下文生成单点候选；
7. 未通过审核的候选不得进入正式营养计算。

所有模糊数量候选进入离线审核表，至少展示菜名、食材、原始表达、步骤上下文、建议克重、确定性计算过程、候选依据和审核状态。用户可选择通过、修改后通过或拒绝。正式运行产物只保存最终批准克重，不携带审核状态、置信度、来源或解释。

密度、单位重量和可食部比例采用规则级审核：同一食材和规格审核一次后批量应用。无法取得可靠规则时不默认使用 `1ml=1g`，对应食材数量保持不可用。

## 6. 原始投料营养

### 6.1 固定营养维度和单位

每份营养参考均为每 100g 可食部：

| 字段 | 单位 |
|---|---|
| `energy_kcal` | kcal |
| `protein_g` | g |
| `fat_g` | g |
| `carbohydrate_g` | g |
| `fiber_g` | g |
| `sodium_mg` | mg |
| `calcium_mg` | mg |
| `iron_mg` | mg |
| `cholesterol_mg` | mg |

模型不得生成这九项营养数值。

### 6.2 数据来源和匹配

项目为非商业用途，营养来源顺序固定为：

1. 中国疾病预防控制中心营养与健康所食物成分数据；
2. USDA Foundation Foods；
3. USDA SR Legacy；
4. USDA FNDDS；
5. 仅在品牌和规格完全一致时使用 USDA Branded 或生产商标签。

匹配必须同时核对标准食材身份、品种、加工状态、生熟状态、干湿状态和可食部口径。`datas/processed/Ingredients/Ingredients2Nutrition.csv` 只能提供候选，旧 FDC ID 和旧数值必须重新验证。

权威来源缺少某项营养时：

- 经食材类别确认的纯植物食材，`cholesterol_mg=0`；
- 经食材类别确认的纯动物食材，`fiber_g=0`；
- 其他缺失保持空值，不使用相似食材代理，也不填零。

### 6.3 可食部与计算公式

可食部折算不属于烹饪得率：

```text
edible_input_g_i = standardized_quantity_g_i × edible_fraction_i
nutrient_total_n = Σ(edible_input_g_i ÷ 100 × nutrient_per_100g_i,n)
raw_nutrient_per_100g_n = nutrient_total_n ÷ Σ(edible_input_g_i) × 100
```

明确写有净肉、去皮、去骨或虾仁时，可食部比例为 1；整鱼、带骨肉、带壳食材使用已审核权威可食部比例。

计算使用十进制定点数，中间过程不舍入，正式输出四舍五入保留两位小数。

每道菜输出：

```text
available
raw_edible_input_weight_g | null
raw_nutrition_total | null
raw_nutrition_per_100g | null
```

任一计入营养的食材缺少批准克重、可食部、唯一营养映射或九项中的非结构性营养值时，整道菜 `available=false`，其重量、总量和每 100g 数值全部为空。禁止输出部分营养合计。

该结果只表示原始可食投料，不表示成品、每份或个人实际摄入量。

## 7. 原子步骤、时长与任务图

### 7.1 原子化和显式时长

步骤从 V2 原始文本重新构建，不复制 `datas` 的旧 1 分钟兜底或下限总时长。每个原子步骤具有稳定 `atom_id`、原始步骤索引和原文片段。

显式解析支持秒、分钟、小时、小数、半小时、四分之一小时、范围和隔夜等表达。范围取中点，最终只保留一个 `duration_seconds`。`食材准备`、`备用`、`尽情享用`等无实际任务内容的步骤标记为 `non_task` 且时长为 0。

### 7.2 两阶段模型补全

对每道菜一次性提交菜名、标准食材和完整原子步骤：

1. 第一次模型调用为全部步骤生成任务类型、资源和依赖候选，但只为缺失时长的步骤生成 `duration_seconds`；
2. 程序校验完整覆盖、ID 唯一、显式值未覆盖、依赖无环、资源合法和时长边界；
3. 第二次独立模型调用复核图是否符合原步骤、是否漏掉等待、是否错误允许并行；
4. 关键冲突或非法结果进入待审清单，不生成可用时间画像。

模型不得删除、合并或改写原子步骤，不得返回区间、置信度、来源或解释。

包含“放入烤箱并烤 30 分钟”等启动动作与无人值守过程的复合描述，必须在原子化阶段拆成启动/放置任务和设备运行任务，避免把整段设备运行时间错误占用厨师。

每个任务固定包含：

```text
atom_id
duration_seconds
task_type: manual | attended_equipment | unattended_equipment | passive | non_task
depends_on[]
resources[]
```

人工操作和持续翻炒等 attended 任务占用厨师；无人值守加热占用设备但不占用厨师；发酵、冷藏等 passive 任务只受依赖约束。`manual` 和 `attended_equipment` 的模型估算上限为 6 小时，`unattended_equipment` 和 `passive` 上限为 7 天，`non_task` 必须为 0。原文明确时长可以在通过解析合法性校验后保留。

缓存键固定为：

```text
recipe_id + ordered_atoms_hash + prompt_version + model_id
```

步骤、Prompt 或模型变化时必须重新估算，不得因 build ID 改变而无条件浪费已有有效缓存。

### 7.3 默认厨房和 CP-SAT 调度

默认家庭厨房资源为：

| 资源 | 容量 |
|---|---:|
| 厨师 | 1 |
| 灶眼 | 2 |
| 烤箱 | 1 |
| 蒸制设备 | 1 |
| 微波炉 | 1 |
| 料理机 | 1 |

冰箱和操作台暂不设容量互斥。不同菜谱之间没有依赖，只通过共享厨师和设备资源产生互斥。

OR-Tools CP-SAT 为每个任务建立 interval，强制执行：

- `depends_on` 前驱完成后才能开始；
- 同一厨师资源不能重叠；
- 超出设备容量的任务不能重叠；
- unattended 和 passive 任务在资源允许时可与厨师操作并行；
- 目标是最小化所有菜谱终端任务的最大结束时间。

单菜画像输出 `active_seconds` 和 `estimated_elapsed_seconds`；菜单输出 `estimated_makespan_seconds`。冷藏、浸泡、发酵和隔夜等待均计入总完工时间。

用户提出“30分钟内”时，只有预计 makespan 不超过 30 分钟的方案才能通过时间过滤。由于部分时长由模型估算，对外只能表述为“预计需要 X 分钟”或“按当前步骤估算可在 X 分钟内完成”，不得承诺保证。

运行时不保留旧的置信度、来源、范围或三值 strict-time 权威字段。任务图不完整的菜品时间不可用，也不参与时间限制筛选。

## 8. 下游消费者契约

### 8.1 B4 健康过滤

B4 继续作为健康安全的唯一权威。它可以读取菜品的标准食材、条件关系和默认备选项，但不读取计算后的营养数值或步骤时长。可选食材保留条件语义，不能被误当成必然投料。

### 8.2 B5 时间

B5 只读取已发布 `step_tasks`，在线不调用模型。B5 对单菜提供预计耗时，对菜单调用 CP-SAT 生成资源约束下的预计 makespan。

### 8.3 B6 营养

B6 只读取 `available=true` 的原始营养画像。没有明确营养目标时不产生通用营养分；有高蛋白、低钠等目标时，基于 `raw_nutrition_per_100g` 在安全候选间进行目标相关判断或软排序。营养不可用时移除该评分维度并重新归一化其他权重，不伪造默认分数。

### 8.4 C2/C3

C2 只在 B4 安全候选中组合菜单，并消费 B5/B6 的正式结果。明确时间限制按预计 makespan 硬筛；C3 只能复述结构化结果，不能自行估时、算营养或扩大健康结论。

其他用户画像和查询工具通过版本化 consumer view 继续读取其既有事实。改变 RAG、营养或时间实现不得改变它们的主键、用户身份或健康事实所有权。

## 9. 质量门禁与失败语义

### 9.1 RAG 门禁

- 每个 eligible 菜品恰好一条 RAG 文档；
- 源标签投影无丢失；
- eligible 菜品餐次标签非空；
- payload keyword 索引完整；
- RAG 不含营养、时长、用户画像或 B4 结论；
- 明确餐次无结果时不得放宽过滤。

### 9.2 营养门禁

- 每个 eligible 菜品恰好一条营养画像；
- `available=true` 时重量、总量和每 100g 九项全部存在且非负有限；
- `available=false` 时三组数值全部为空；
- 模糊数量未审核、营养映射不唯一或非结构性营养缺失不能进入部分合计；
- 每次构建报告营养可用率、不可用原因分类和相对上一批准构建的变化；覆盖率下降必须得到人工批准。

营养不可用是允许的正式状态，不阻止该菜进入 RAG、B4 或无营养目标的菜单流程。

### 9.3 时间门禁

- 每个 eligible 菜品必须有完整、无环、全步骤覆盖的时间任务图；
- 每个真实任务恰好一个合法 `duration_seconds`；
- `non_task=0`，其他任务为正整数；
- 所有资源代码、依赖 ID 和设备容量合法；
- 模型不能覆盖显式时长；
- CP-SAT 必须能为每个单菜样例产生可行调度。

时间图冲突未解决时 staging build 不得进入 ready 状态。

### 9.4 跨域门禁

- RAG、营养、时间、MySQL 和 Qdrant 使用同一 build ID；
- eligible `recipe_id` 集合在三类画像中完全一致；
- B4 输入不含营养和时长；
- B5/B6 只消费 B4 后候选；
- 用户画像、健康关系和菜品身份无孤儿引用；
- Schema 主版本改变时所有消费者和初始化器必须在同一变更中升级。

## 10. 测试设计

### 10.1 语义重写与 RAG

黄金查询至少覆盖：

- “推荐早餐”只返回早餐；
- “推荐晚餐”不混入仅早餐菜品；
- “老人吃的晚餐”同时生成晚餐硬过滤和老人语义标签；
- “不要辣、不要花生”保持否定；
- “换几个清淡点的”继承上一轮餐次和人群；
- 重写响应非法时正确重试和回退；
- 同字段 OR、跨字段 AND、排除 `must_not`；
- 无结果时不移除硬过滤。

### 10.2 数量与营养

单元测试覆盖明确质量、范围中点、明确约数、密度、单位重量、可食部、食材状态、条件食材、步骤补充食材和过程材料排除。手算样例验证九项营养总量和每 100g 公式。

失败样例覆盖未审核模糊数量、缺营养、歧义映射、错误结构性零值、可选项误计入和 `available=false` 部分合计。

### 10.3 时间任务图

测试覆盖：

- 显式秒/分/小时、小数、范围中点和隔夜；
- 非任务 0 秒；
- 串行依赖；
- 两个灶眼并行；
- 炖煮期间切配；
- attended 任务同时占用厨师与设备；
- 设备互斥；
- 多菜跨菜穿插；
- 依赖环、丢失 ID、重复 ID、非法资源和显式时长覆盖；
- 30 分钟预计 makespan 硬筛。

### 10.4 全局回归

运行现有单元、集成、端到端、readiness 和跨域验证套件。额外核对所有 19 类固定 Artifact 的主键、计数、Schema 版本和 build identity，并验证现有用户画像、健康过滤、菜单调整和回答投影不发生职责漂移。

## 11. 分阶段实现、自检与发布

实施按以下阶段推进：

1. Schema、契约和测试基线；
2. 菜品标签、条件食材和数量审核产物；
3. 语义重写与 RAG payload/过滤；
4. 营养参考、克重审核和原始营养计算；
5. 原子步骤、双阶段模型补全和 CP-SAT 任务图；
6. B4/B5/B6/C2/C3 消费者接线；
7. 全量重建、审核、端到端验证与原子切换。

每完成一个阶段必须执行：

- 本阶段单元测试；
- 相关集成测试；
- Schema 和 Artifact diff；
- 对照本设计检查权威边界；
- 检查工作区差异，避免覆盖无关用户修改；
- 更新实施记录后再进入下一阶段。

最后一次全局审视必须从完整请求链检查：语义重写是否丢约束、RAG 是否越权、B4 是否仍为健康唯一权威、营养和时间是否只在 RAG 后消费、BuildManifest 是否一致、MySQL/Qdrant 是否原子同步，以及旧消费者是否存在字段冲突。

只有全局测试、质量门禁和全部人工数量审核均形成明确决定后，才切换 ready build。审核拒绝是合法决定，但对应菜品营养必须保持不可用。回滚通过恢复上一 ready build 指针完成，不删除上一构建。

## 12. 已批准决策摘要

- RAG 前必须通过模型进行语义识别和口语化查询重写；
- 全部原始标签和菜品画像进入向量文本与 payload；
- 健康、时间和营养在 RAG 后执行；
- `datas` 只作候选和审计参考；
- 模糊克重与毫升候选必须经用户审核；
- 正式数量统一为克，明确范围取中点，明确约数保留数字；
- 可食部折算启用，规则级审核后批量应用；
- 原始营养同时输出整份总量和每 100g 原始可食投料值；
- 非权威缺失保持空值，结构性零值仅按已确认食材类别填写；
- 任一参与食材缺完整营养时整道菜营养不可用；
- 非任务步骤 0 秒，真实步骤必须有单点时长；
- 时间使用双阶段模型补全、依赖图和 CP-SAT 调度；
- 默认一名厨师、两个灶眼及固定家庭厨房设备；
- 被动等待和提前准备计入总完工时间；
- 时间限制按预计 makespan 硬筛，但不作保证性承诺；
- 每阶段完成后局部审查，最终进行全局冲突与职责边界审查。
