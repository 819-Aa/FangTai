# 健康关系矩阵最小化复核设计

**日期：** 2026-08-13  
**状态：** 待用户复核  
**范围：** 过敏关系的已知疑似假阴性与现有 `hard_exclude`，不扩展疾病、指标或特殊人群规则

## 1. 目标

在不把推荐系统整体变得更保守的前提下，修复能够由现有食材身份、明确别名或明确成分直接证明的过敏关系错误，同时检查现有 985 条 `hard_exclude` 是否存在明显误杀。

本次复核不追求重新定义全部 65,854 条健康关系，也不把“建议少吃”“可能不适合”“营养指标较高”升级为硬排除。

## 2. 范围边界

### 2.1 纳入范围

1. `data/review/health_relation_audit_2026-08-13.txt` 中的 96 条过敏候选；
2. `data/review/health_relation_decisions.csv` 中现有 985 条 `hard_exclude`；
3. 生成候选和校验决定所需的食材规范名、别名、拆分关系及可用成分证据；
4. 与本次实际变更对应的健康矩阵测试、审计记录和交付说明。

### 2.2 明确排除

1. 不新增或扩大疾病、健康指标、儿童、老年、孕期、哺乳期的硬排除规则；
2. 不因为高糖、高盐、高脂、高嘌呤等一般营养倾向自动设置 `hard_exclude`；
3. 不把名称关键词命中直接等同于最终决定；
4. 不修改信息不足或存在合理歧义的关系；
5. 不在本次任务中重构整个健康规则体系。

## 3. 判定原则

每条待复核关系只允许以下三种复核结果：

| 复核结果 | 含义 | 对矩阵的动作 |
|---|---|---|
| `confirmed_change` | 现有决定与明确食材身份、别名或成分事实直接矛盾 | 修改决定 |
| `confirmed_keep` | 候选属于名称误报，或现有硬排除有明确事实支持 | 保持决定 |
| `insufficient_evidence` | 仅凭名称或现有资料无法可靠判定 | 保持现状并记录原因 |

从 `no_hard_relation` 改为 `hard_exclude`，至少满足下列一种条件：

1. 规范食材名本身就是相应过敏原，例如“坚果”“花生”“蛋清”；
2. 已批准别名明确等价于相应过敏原；
3. 固定数据中的拆分关系或成分事实明确包含相应过敏原；
4. 项目已经采用的权威资料明确把该食材归入对应过敏原类别。

以下情况不得仅凭关键词改为 `hard_exclude`：

- 风味或商品描述，例如“蟹味菇”；
- 名称巧合，例如“贝贝南瓜”“川贝”；
- 可能因品牌或配方变化而含过敏原，但固定数据没有成分事实；
- 仅存在交叉污染可能；
- 只属于一般饮食限制、建议限量或营养偏好。

复查现有 `hard_exclude` 时采用对称标准：若名称、别名、拆分关系和现有证据均不能支持对应过敏原，且能够确认是词形误报，则改为 `no_hard_relation`；信息不足时保持原决定。

## 4. 数据产物

### 4.1 可审计复核表

创建机器可读 CSV，每行对应一个被检查的矩阵单元，至少包含：

```text
constraint_code
ingredient_id
ingredient_name
source_set
current_decision
review_result
proposed_decision
reason_code
reason
evidence
```

`source_set` 取值为 `false_negative_candidate` 或 `existing_hard_exclude`。复核表不得使用虚构个人姓名，也不需要签字字段。

### 4.2 矩阵修改

只有 `review_result=confirmed_change` 的行可以修改 `health_relation_decisions.csv`。每项修改必须能够通过复核表定位到原因和证据。`confirmed_keep` 与 `insufficient_evidence` 不修改矩阵。

### 4.3 摘要报告

报告至少给出：

- 96 条候选的三类结果计数；
- 985 条现有硬排除的三类结果计数；
- 实际修改的关系清单；
- 未修改歧义项及原因；
- 修改前后 `hard_exclude`/`no_hard_relation` 数量；
- 矩阵完整性、唯一性和封闭枚举验证结果。

## 5. 处理流程

1. 从固定 Artifact 读取规范食材身份、别名、拆分关系和可用成分事实；
2. 载入 96 条疑似假阴性和 985 条现有硬排除，按 `(constraint_code, ingredient_id)` 去重；
3. 对每条关系按第 3 节的对称标准形成复核结果；
4. 先产出复核表和摘要，不直接修改矩阵；
5. 校验复核表无缺行、重复行、非法结果或无理由决定；
6. 仅应用 `confirmed_change`；
7. 重新验证 65,854 个键完整且唯一、决定枚举合法、已知正反例正确；
8. 若矩阵变化影响固定 Artifact，则在获得数据重建授权后另行重建并验证。本设计本身不授权初始化、清空或覆盖正在运行的数据服务。

## 6. 测试与验收

实施必须采用测试先行，至少覆盖：

1. 明确正例：`坚果/混合坚果/综合坚果 → allergy_tree_nut` 被识别为 `confirmed_change`；
2. 明确误报：`蟹味菇 → allergy_crab`、`贝贝南瓜 → allergy_seafood/shellfish` 不得变成 `hard_exclude`；
3. 信息不足：复合调味品没有固定成分证据时保持现状；
4. 现有硬排除复查：明确过敏原保持，明确词形误报才撤销；
5. 复核表恰好覆盖两个输入集合去重后的全部关系；
6. 只有 `confirmed_change` 能进入矩阵变更；
7. 矩阵仍为 38 × 1,733 = 65,854 个唯一键；
8. `ruff`、B1/B4 健康关系测试和相关集成测试通过。

## 7. 完成标准

满足以下全部条件才可认为本次最小复核完成：

1. 96 条候选与 985 条现有硬排除全部有可审计结果；
2. 无关键词直接自动批准或自动撤销；
3. 所有实际变更都有确定理由和可追踪证据；
4. 歧义项保持原决定，不扩大硬排除；
5. 自动测试和矩阵完整性检查通过；
6. 若尚未获得运行数据重建授权，明确区分“源矩阵已更新”和“运行 Artifact 尚未重建”。
