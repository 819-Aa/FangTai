# 1932 道菜营养补全与 H06 发布设计

> 状态：IN_REVIEW
> 日期：2026-08-23
> 适用项目：`program_v2`
> 前置设计：`2026-08-21-recipe-rag-nutrition-time-design.md`

## 1. 背景与问题

H05 已发布 1932 道 eligible dish 的菜品画像、RAG、健康关系、时间画像和依赖关系，但营养画像尚未形成可用数据：

- `nutrition_features` 共 1932 条，`available=true` 为 0；
- 当前表面失败原因为 `edible_fraction_missing=1559`、`quantity_unapproved=373`；
- 实际有 4372 条待决数量 occurrence，影响 1501 道菜；
- 正式可食比例规则为空；
- 正式 nutrition crosswalk 为空；
- 解除数量和可食比例阻塞后，全部菜仍会进入 `mapping_missing`；
- 当前 G15 可用营养基线为 0，因此“1932 道全部不可用”仍能通过构建。

本设计补齐全部菜品的原始可食投料营养，使营养能够在用户明确提出营养目标时影响推荐排序，同时保持 RAG、健康硬过滤、时间处理和菜单规划的既有职责边界。

## 2. 目标与非目标

### 2.1 目标

1. 1932 道 eligible dish 均发布完整、可计算的九维营养画像；
2. 用规则级批量审批替代 4372 条 occurrence 逐条人工审批；
3. 营养只在 RAG 和 B4 健康过滤后参与内部软排序；
4. 用户未明确提出营养目标时，不生成通用营养分且不改变普通推荐结果；
5. 在全新的 H06 容器组中完成构建、验证和切换，不覆盖 H05；
6. 通过质量门禁阻止缺失值、伪造零值、歧义映射和构建版本不一致进入 ready build。

### 2.2 非目标

- 不计算烹饪得率、营养保留率或烹饪损耗；
- 不计算成品重量、每份营养、个人摄入量、人数份量或采购量；
- 不使用营养值制造、抵消或修改 B4 健康硬结论；
- 不在普通回答和前端中展示内部营养数值、来源、置信度或评分；
- 不用模型直接生成九项营养数值；
- 不在本次数据工程中改造“会话前不强制加载健康档案”，该项在 H06 数据工程完成后单独讨论。

## 3. 不可变的系统边界

请求链固定为：

```text
用户原始输入
→ 口语化语义重写与约束校验
→ C1 RAG 菜品筛选
→ B4 健康硬过滤
→ B5 时间处理 + B6 营养软评分
→ C2 菜单组合
→ B4 最终健康复核
→ 回答
```

- C1 只读取菜品画像和 label，不读取营养、时间、用户健康画像或健康结论；
- B4 是健康安全的唯一权威，不读取计算后的营养值；
- B5/B6 只消费 B4 输出的当前请求安全候选；
- C2 不能把 B4 排除的菜放回菜单；
- 87 条套餐/备料和 11 条烹饪程序的固定依赖关系不得因营养构建而改变；
- 其他用户画像查询工具的主键、身份和健康事实所有权不得改变。

## 4. 数量标准化设计

### 4.1 规则层级

数量标准化按以下优先级执行：

1. occurrence 级明确批准决定；
2. 确定性质量单位换算；
3. 已批准的“食材 + 形态 + 单位”单件重量规则；
4. 已批准的“食材 + 形态”密度规则；
5. 已批准的“食材 + 用途 + 形态”模糊用量单值规则；
6. 无法唯一命中的记录进入异常队列。

明确的克、千克、斤、两直接机械换算。“半、一、两 + 明确单位”由确定性解析器转换。毫升和升只能结合批准密度换算；勺、杯、碗、个、片、根等使用单位重量规则，不能误用密度。

现有 `MeasureRule` 只有“食材 + 单位”键，不能直接支持本设计。H06 必须先发布版本化的数量规则 Schema：

- `unit_weight` 键：`ingredient_id + normalized_form + normalized_unit`；
- `density` 键：`ingredient_id + normalized_form`；
- `fuzzy_single_value` 键：`ingredient_id + normalized_form + usage_code + fuzzy_token_class`；
- `usage_code` 使用封闭枚举：`main`、`supporting`、`seasoning`、`cooking_fat`、`retained_liquid`；
- `fuzzy_token_class` 使用封闭枚举归并“适量、少许、数个、几滴”等原文表达；
- `RecipeNutritionInputView`/`NutritionOccurrenceInput` 升级版本并携带 `usage_code` 和 `fuzzy_token_class`；
- `usage_code` 由 B1 根据标准食材类别、结构化步骤绑定和是否实际留在菜中确定；无法唯一确定时写入 occurrence 级用量/用途审核决定，不允许模型在线决定。

H06 构建只读取新版输入视图和新版规则；不得让同一个 build 混用旧键和新键。

### 4.2 规则级批量审批

同一规则组满足以下条件时，可以生成一个批量规则候选：

- 同组有效样本不少于 5 条；
- 候选值离散程度不超过 15%；
- 食材、食用形态、单位和用途无冲突；
- 候选值均为正数且未命中异常门禁。

“至少 5 条、离散程度不超过 15%”只用于证明规则组稳定，不能单独证明物理值正确。从样本归纳的规则仍须经过主审一次；批准后才批量应用到所有命中 occurrence。

统计公式固定为：

- 分组键必须与对应正式规则键完全一致；
- 离散程度使用变异系数 `CV = 样本标准差 ÷ 算术平均值`，平均值必须大于 0；
- “偏差超过 30%”定义为 `abs(candidate - approved_rule_value) ÷ approved_rule_value > 0.30`；
- IQR 使用升序样本的 nearest-rank 四分位数：`Q(p)=x[ceil(p×n)-1]`，异常范围为 `[Q1-1.5×IQR, Q3+1.5×IQR]`；
- 计算全部使用 `Decimal`，比较前不做显示精度舍入。

### 4.3 异常队列

以下情况不得自动落正式规则：

- 主料数量为空或只能依靠模型估算；
- “数、几、适量、少许、几滴”等无法命中已批准单值规则；
- 盐、油、糖、酱油等对钠、脂肪或能量影响较大的模糊用量；
- 模型候选与规则值偏差超过 30%；
- 候选值落在同组 `1.5 × IQR` 异常范围之外；
- 食材形态、用途或是否实际留在菜中不明确。

子代理可以提出候选，主代理负责规则级审核。只有无法可靠判断、且会明显改变营养排序的关键异常提交用户决定。

所有批准异常必须写入机器可复验的 `quality_exception_decisions` Artifact，至少包含 `exception_id`、`check_code`、`entity_type`、`entity_id`、观测值、阈值、最终决定和 `review_status`。只有 `approved/modified` 可以关闭异常；口头说明或 Markdown 记录不能使门禁通过。

## 5. 可食比例设计

可食比例规则的键至少包含标准食材和投料形态。已经是净料或可直接食用形态时可以使用 `1.0`；整鱼、带骨肉、带壳海鲜、带皮或带核果蔬等必须使用对应形态规则，不能统一设为 `1.0`。

H06 增加 occurrence 级 `ingredient_edible_fraction_decisions`。优先级固定为：

1. occurrence 级 `approved/modified` 决定；
2. `ingredient_id + normalized_form` 通用规则；
3. 未命中则进入异常队列。

如果同名食材的空白形态分别表示净料和带皮/带骨原料，必须先批准形态补全，或写 occurrence 级可食比例决定；不得让空白形态通用规则覆盖两种事实。

自动规则必须满足：

- 食材身份和形态唯一；
- 比例大于 0 且不大于 1；
- 与数量规则的投料形态一致；
- 不把烹饪得率、吸水率或营养保留率混入可食比例。

跨形态、整料拆解方式不清或不同参考差异较大的记录进入异常队列。

## 6. 营养参考与 Crosswalk

### 6.1 映射优先级

正式映射优先级固定为：

1. 名称和食用形态完全一致；
2. 已批准的同义名称，实际食材和形态一致；
3. 同类别、同食用形态的最近可比食材；
4. 无法满足上述条件时补充权威参考或进入异常审阅。

参考选择优先使用项目已有的中国食物成分参考，其次使用 USDA Foundation、SR Legacy 或 FNDDS 等项目已有记录；品牌食品只允许名称、品牌和规格完全一致时 exact 匹配。需要新增参考时仅使用权威、可稳定复核的数据。项目为非商业用途。

### 6.2 近似映射边界

近似映射只有同时满足下列条件时，才可由子代理提出并由主代理批准：

- 同一食材类别；
- 同一实际食用形态；
- 不跨生熟、干湿、泡发前后；
- 不跨明显不同物种或营养组成；
- 不是复合调味品、配方食品或规格不明的品牌食品；
- 被选参考九维营养完整。

跨类别、跨形态、跨物种、复合食品、多候选无法唯一决策或可能显著改变排序的映射提交用户审阅。

现有 crosswalk 只接受 `exact/approved_alias`，无法表达“最近可比食材”。H06 将离线 `match_method` 扩展为：

- `exact`：名称和形态完全一致；
- `approved_alias`：同一实际食材的批准同义名；
- `approved_comparable`：不同名称但满足本节全部最近可比条件的批准参考。

`approved_comparable` 必须显式保存 ingredient/form 到唯一 reference ID 的决定，并通过类别、形态、九维完整性和唯一性校验。该方法只存在于离线 crosswalk 和内部构建审计，不进入用户回答，也不等同于置信度字段。

### 6.3 完整性和零值

模型不得填营养值。任一非结构性营养维度缺失时，不能用 0、均值或模型估计补齐。只有在食材身份和来源类型已明确、且该维度属于结构性不存在时，才允许使用结构性零值；否则选择九维完整的同形态参考或进入异常队列。

H06 增加正式 `nutrition_reference_food_origins` 审核 Artifact，以 `reference_id` 为唯一键，封闭值为 `plant/animal/mixed/unknown`。只有批准的 `plant` 可以补植物胆固醇结构性零值，只有批准的 `animal` 可以补动物膳食纤维结构性零值；`mixed/unknown` 不允许产生结构性零值。该字段表示食物组成类型，不是面向用户的数据来源说明。

正式运行时营养 Artifact 不增加来源、置信度或解释字段。离线参考库只保留计算和审查所必需的参考标识，不向推荐结果和前端暴露。

## 7. 原始投料营养计算

固定九个维度及单位为：

- `energy_kcal`
- `protein_g`
- `fat_g`
- `carbohydrate_g`
- `fiber_g`
- `sodium_mg`
- `calcium_mg`
- `iron_mg`
- `cholesterol_mg`

对每个参与计算的食材 occurrence：

```text
edible_grams_i = normalized_grams_i × edible_fraction_i
nutrient_total_j = Σ(edible_grams_i ÷ 100 × reference_nutrient_i,j)
raw_nutrition_per_100g_j = nutrient_total_j ÷ Σ(edible_grams_i) × 100
```

同时发布整道菜原始可食投料总克重、九项营养总量和每 100 克九项营养。

### 7.1 食材计入边界

- 必选食材计入；
- `one_of` 只计算已经确定的默认项；
- `optional` 默认不计入基础营养；
- 实际留在菜中的水、油和调味料计入；
- 清洗水、焯水、泡发后倒掉的水、蒸制垫片、废弃腌料和其他过程材料不计入；
- 不根据最终成品状态修正重量和营养。

### 7.2 All-or-nothing

任一计入食材缺少批准克重、可食比例、唯一 crosswalk 或九维完整参考时，整道菜不得发布部分营养。构建中保留稳定失败原因用于定位，但 H06 最终 ready build 不允许存在 unavailable 菜品。

## 8. B6 营养软评分

B6 支持以下明确目标：

| 目标 | 维度 | 方向 |
|---|---|---|
| `high_protein` | `protein_g` | 越高越好 |
| `low_sodium` | `sodium_mg` | 越低越好 |
| `high_fiber` | `fiber_g` | 越高越好 |
| `low_fat` | `fat_g` | 越低越好 |
| `high_calcium` | `calcium_mg` | 越高越好 |
| `high_iron` | `iron_mg` | 越高越好 |

评分只使用 `raw_nutrition_per_100g`，并在当前 B4 安全候选集内计算相对百分位。多个目标暂时等权平均。

现有 C2 多策略权重继续保留：营养在不同方案中占 15% 至 50%，至少生成一个 `nutrition_heavy` 方案。营养是实质性软排序，但绝不能越过 B4 健康硬过滤。

没有明确营养目标时：

- B6 的 `weighted_total=None`；
- C2 禁用营养维度并对其余可用维度重新归一化；
- 不生成通用“健康分”；
- 营养数据补全不得改变普通推荐结果。

## 9. 语义重写约束

RAG 前增加的模型负责口语化改写和结构化识别，但它不是约束权威。它可以标准化用户明确表达的餐次、人群、口味、菜品类型和营养目标，并为结构化字段给出对应原话证据。

营养目标必须由用户原话中的受控显式表达产生。模型不得把“健康一点”“营养均衡”等泛化表达扩展成高蛋白、低钠、低脂等具体目标。规范化层必须：

- 校验目标 code 在允许集合中；
- 校验目标存在可追溯的用户原话表达；
- 拒绝模型新增的无证据目标；
- 保留用户明确的餐次、人群、禁忌和营养条件；
- 不允许重写模型作健康排除、营养计算或最终推荐决定。

同时完善运行时审计 Artifact：营养不可用必须记录为维度禁用，不能表示成营养得分 0。

为避免破坏现有 `FeasibleMenu.nutrition_score: float` 消费者，H06 采用向后兼容的增量字段：

- 保留现有数值字段的结构；
- 新增 `nutrition_dimension_enabled: bool`；
- 新增 `nutrition_disabled_reason: str | null`；
- 只有 `nutrition_dimension_enabled=true` 时，`nutrition_score` 才具有评分语义；
- 旧的数值 `0` 不能再单独被解释为“营养差”或“营养不可用”。

H06 API、C2、C3 和审计消费者同步升级 Artifact Schema 版本；H05 继续使用原版本，两个运行实例不得混用 Artifact。

## 10. 数据质量门禁

H06 ready build 必须同时满足：

1. eligible dish 恰好为 1932 道，且每道恰好一条营养画像；
2. 营养可用数必须等于本次 BuildManifest 的 eligible dish 数，H06 的明确验收值为 `1932/1932`；
3. 未解决 quantity、edible fraction、crosswalk、nutrient completeness 均为 0；
4. 九项总量和每 100 克值全部存在、为有限非负数；
5. 营养总量、每 100 克值和可食投料总克重同时存在；
6. 规则键和 crosswalk 键唯一；
7. 同一食材形态不得映射到多个正式参考；
8. 当前 G14 all-or-nothing 门禁继续保留；
9. G15 从固定基线 0 改为 `available_count == manifest.eligible_recipe_count`，H06 同时断言 expected eligible count 为 1932；
10. 能量、钠、脂肪、总重量及映射结果的异常报告为空，或每项都有明确批准决定；
11. MySQL、Qdrant、RAG、营养、时间、依赖关系和 BuildManifest 使用同一个 `build_id`。

异常检查固定为两层：

- 硬合法性：可食投料总克重大于 0；每 100 克蛋白质、脂肪、碳水和膳食纤维分别位于 `[0,100]`；能量位于 `[0,900] kcal`；四项克数合计不超过 110；九维均为有限非负数。硬合法性失败不能用异常批准绕过；
- 复核异常：按 `dish_type` 分组（组内不足 20 道时使用全体）计算 nearest-rank `Q1/Q3`，落在 `[Q1-3×IQR,Q3+3×IQR]` 外的可食总重量或任一每 100 克营养值进入异常队列；此外能量超过 750 kcal/100g、脂肪超过 80g/100g、钠超过 5000mg/100g 直接进入异常队列。

复核异常可以由机器可复验的 `quality_exception_decisions` 关闭，但不能改变原计算值。所有异常检查使用稳定 `check_code + entity_id` 生成 `exception_id`，确保重新构建可以复验同一决定。

以下正式审核输入必须纳入 SourceManifest 并参与哈希：

- 版本化 `ingredient_measure_rules.csv`；
- `ingredient_quantity_decisions.csv` 和新增的 nutrition usage occurrence decisions；
- `ingredient_edible_fraction_rules.csv` 和新增的 occurrence decisions；
- `ingredient_nutrition_crosswalk.jsonl`；
- 新增的 `nutrition_reference_food_origins`；
- 新增的 `quality_exception_decisions`。

任何门禁未通过时，H06 不得成为 ready build。禁止通过伪造零值、默认均值或降低门禁完成发布。

## 11. H06 独立发布

H05 不被原地修改。发布顺序为：

1. 在独立构建目录生成 H06 数据和唯一 build ID；
2. 创建独立的 H06 MySQL、Qdrant、Redis 容器和数据卷；
3. 启动独立的 H06 API 进程/容器，使用 H06 代码版本和 H06 数据配置；
4. H06 API 必须从空进程加载 C1/B4/B5/B6/C2，禁止复用 H05 的进程级单例和缓存；
5. 将全部同构建产物初始化到 H06；
6. readiness 同时核对 C1/B4/B5/B6 所持有的 ready build ID 与 H06 BuildManifest；
7. 运行数据门禁、单元测试、集成测试和接口健康检查；
8. 核对 H06 与 H05 的非营养差异；
9. 验证通过后，将对外入口原子切换到独立 H06 API；
10. H05 的代码版本、API 进程配置和数据容器整体保留为回滚单元；
11. 回滚时切换回 H05 API，而不是让 H06 进程重新连接 H05 数据；
12. 只有 H06 稳定运行并得到用户明确授权后，才删除 H05。

## 12. 全局兼容检查

H06 发布前必须检查：

- 1932 道菜的 recipe ID、名称和原始 label 未意外变化；
- 原 label 已有餐次时，模型不得增加餐次；只有原 label 完全缺餐次时才允许使用批准补全；
- G12 的 expected meal tags 必须从固定原始 CSV 和正式 `data/review/recipe_profile_enrichment.jsonl` 的 `review_status=approved` 记录独立重算；不得从 retrieval view 反推 expected 值；
- `recipe_profile_enrichment.jsonl` 继续作为 SourceManifest 中可复验的正式构建输入，以修复 raw meal tags 为空时 enrichment 结果可能自我授权的漏洞；
- RAG 文档包含允许的菜品画像和 label，但不含营养、时间、用户画像或健康结论；
- 87 条套餐/备料和 11 条烹饪程序的固定依赖保持不变；
- B4/B5/B6/C1/C2 的消费者边界和主键保持不变；
- 用户画像和其他工具接口不受营养构建影响；
- 构建清单、数据库记录和向量点数量一致；
- 不将本次工作扩展为会话启动流程改造。

## 13. 测试与验收场景

### 13.1 数据计算

- 明确质量、密度、单位重量、半个/两个等确定性换算；
- 模糊用量规则命中与异常队列；
- 可食比例形态隔离；
- exact、approved alias 和最近可比映射；
- 生熟、干湿、物种、复合食品的拒绝样例；
- 手算样例验证九项总量和每 100 克公式；
- 任一前置事实缺失时 all-or-nothing；
- 1932 道营养画像完整性与异常分布。

### 13.2 推荐链路

- “推荐一些老人吃的晚餐”：餐次和人群参与 C1，随后进入 B4；
- “推荐低钠晚餐”：只有明确低钠目标才启用 B6；
- “推荐高蛋白低脂晚餐”：两个目标等权评分；
- “推荐健康一点的晚餐”：不得产生具体营养目标；
- 无营养目标时，营养维度禁用且普通推荐不被改变；
- 被 B4 排除的菜不能因营养高分重新进入；
- 套餐任一整体条件无法满足健康要求时不推荐，满足时保持固定组合；
- 依赖烹饪程序随对应菜品正确输出。

### 13.3 发布验证

- H06 MySQL、Qdrant、Redis 和 API 健康检查；
- ready build ID 和各 Artifact build ID 一致；
- H05 的代码、API 进程、数据库配置和缓存作为整体回滚路径可用；
- H06 未通过全部门禁时 API 不切换；
- H05 未经用户授权不得删除。

## 14. 子代理执行与审查方式

实施分两轮，每轮最多三个子代理并行，修改边界互斥。

第一轮：

- 子代理 A：数量解析、单位重量、密度和模糊用量规则；
- 子代理 B：可食比例和食材形态规则；
- 子代理 C：营养参考、USDA 候选、crosswalk 和最近可比映射；
- 主代理：规则审核、冲突处理、异常分流和用户关键决策整理。

第二轮：

- 子代理 A：九维营养计算、1932 道覆盖闭环；
- 子代理 B：质量门禁、自动化测试和 H06 构建；
- 子代理 C：语义重写、B6/C2 审计字段和全链路验证；
- 主代理：代码与数据审核、非营养差异核对、全局冲突审查和发布判断。

每完成一部分只做一遍对应专项自检。全部部分完成后，主代理再做一次全局审查，重点核对请求链权限、构建版本、消费者边界、容器隔离和回滚能力。

## 15. 停止条件与用户决策点

以下情况必须停止对应批次并提交用户决定：

- 关键主料只能依赖无参考的模型克重估算；
- 高影响调料无法建立稳定单值规则；
- 近似映射跨类别、跨食用形态或可能显著改变营养排序；
- 权威参考仍无法提供完整九维值；
- 补全会改变菜品身份、原始 label、固定套餐或程序依赖；
- 1932/1932 营养可用门禁无法满足；
- H06 与 H05 出现非预期的非营养差异。

没有重大争议的规则级决定由子代理提出、主代理审核后批量写入，不要求用户逐条审核。

## 16. 完成定义

只有以下条件全部满足，营养数据工程才算完成：

- 设计和实施计划已经用户批准；
- 1932 道菜营养全部可用；
- 所有质量门禁和测试通过；
- 明确营养目标能够实质影响安全候选间排序；
- 无明确营养目标时推荐行为不受营养影响；
- B4 健康权威、RAG 边界、时间模块和固定依赖无回归；
- H06 独立容器通过健康、ready 和回滚验证；
- 用户批准切换到 H06；
- H05 是否删除由用户另行明确决定。
