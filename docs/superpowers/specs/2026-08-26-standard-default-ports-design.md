# H06 标准默认端口切换设计

## 目标

将当前 H06 从项目历史错峰端口切换到各服务的标准默认端口，同时保留已发布的数据卷和 build 身份，并把已定位的语义重写非法标签修复一起上线。

最终端口固定为：

- API：`8000`
- MySQL：`3306`
- Qdrant REST/gRPC：`6333/6334`
- Redis：`6379`

## 方案

继续使用 compose project `food_agent_v2_h06`、现有三个 H06 容器名和现有三个 H06 数据卷。通过 Docker Compose 强制重建容器，只改变宿主机端口映射，不删除数据卷、不重新生成数据画像，也不重复执行 `data-initialize`。

API 使用冷启动切换：当前 `8001` 进程保持到存储重建开始；存储在标准端口恢复 healthy 后，以新代码和标准端口环境在 `8000` 启动新进程。`8000 /ready` 与真实场景通过后关闭旧 `8001`。由于存储容器需要原地重建，会存在短暂维护窗口，不承诺完全无中断。

## 语义重写修复

口语重写模型不得把参与人数当作菜品人群标签。`population_tags` 必须属于闭集；`两人` 无效。普通“健康”也不得被写成疾病或过敏约束。模型连续产生非法输出时，沿用现有三次尝试后确定性 fallback，保留晚餐、清淡、排除海鲜等明确语义。

## 配置与发布契约

同步修改以下默认值和发布契约：

- `docker-compose.yml` 的 MySQL、Qdrant、Redis宿主端口默认值；
- 应用配置与 `.env.example` 的 API/存储默认端口；
- H06 发布脚本、契约测试和运行手册中的端口；
- 相关配置测试和语义重写回归测试。

不更改容器内服务端口，也不改变数据库、Qdrant collection、Redis key prefix、build ID 或固定 Artifact Schema。

## 安全与回滚

操作前确认 `8000/3306/6333/6334/6379` 空闲，并核对 H06 容器只挂载预期的 H06 卷。重建命令不得带 `-v`，不得删除卷。

若标准端口上的存储或 API 未通过 readiness，则停止失败的新 API，以同一 H06 数据卷恢复原映射 `3309/6339/6340/6382`，并在 `8001` 冷启动旧入口。H05 已删除，不作为回滚单元。

## 验收

完成条件：

1. H06 三容器在标准端口全部 healthy，旧 H06 错峰端口不再监听；
2. MySQL ready build ID 仍为 `fefd8bd7-dafa-4cc5-be0a-40ca22939392`，19 类 Artifact 和 1932 道菜计数不变；
3. Qdrant 点数仍为 1932，Redis ready；
4. `http://127.0.0.1:8000/ready` 返回同一 build ID；
5. 非法 `两人` 人群标签回归测试通过，同一多人晚餐真实场景连续通过；
6. 旧 `8001`、`3309`、`6339/6340`、`6382` 不再监听，H05 容器和卷仍为零。
