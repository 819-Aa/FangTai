# V2 回答与前端模块设计

- 状态：`APPROVED`
- 日期：2026-08-09
- 适用项目：`program_v2`
- 上游依据：[系统总体设计](../00-system-overview.md)、[全局不变量](../contracts/global-invariants.md)、[模块边界](../contracts/module-boundaries.md)、[Agent工作流与编排模块](09-agent-workflow.md)、[API与SSE模块](11-api-and-sse.md)

## 0. 2026-08-09 批准的实现基线

- 回答只渲染已验证 Artifact 中的固定菜名、食材、步骤和证据摘要；不得自行改菜、补步骤、估算时间、声称医疗效果或泄露营养内部值。
- 严格时间状态必须分别呈现“已验证满足”“无法验证”“无可行菜单”；软时间偏好只能描述为排序倾向。
- 前端采用匿名参与者槽位与 `participant_ref`，不要求用户输入真实用户 ID、疾病名或他人指标；敏感事实由后端固定档案解析。
- 同一对话持续复用 `session_id`；页面刷新、SSE 重连和多轮修改不得无故创建新会话或丢失已提交菜单引用。
- 前端 Reducer 必须处理创建、运行、`analysis_ready`、`answer_ready`、`result_committed`、失败、取消、重连和重复事件。`answer_ready` 不是最终提交完成。
- 页面只显示 API 明确公开的字段，并为无可行菜单、严格时间未知、系统失败、取消和重连提供不同状态，不用统一“生成失败”掩盖语义。

## 1. 模块目的

D2 定义系统输出给用户的最后两段：回答模型生成的自然语言回答应该说什么、不能说什么，以及前端如何展示已验证的结果而不越界。

D2 不生成回答——那是回答模型的职责。D2 不传输回答——那是 D1 的职责。D2 定义回答和前端必须遵守的边界规则、展示格式和禁止行为。它与 INV-005（回答不得改变已验证菜单）、INV-013（不得暴露其他参与者健康信息）和系统总览 §21（回答与用户可见分析）直接对应。

## 2. 已确认前提

- 回答模型只能描述 `MenuDecisionArtifact` 所选且经 `FinalValidationArtifact=PASS` 的菜单（INV-005）。
- 回答不得增加菜品、替换食材、改写步骤、重组方案。
- 回答不得输出内部营养数值、`per_serving`、疾病名称、原始指标值、参与者真实身份（INV-013）。
- 用户可见分析摘要（`user_visible_analysis`）是已验证证据的说明，不是模型隐藏思维过程。
- 前端只消费 D1 的 SSE 事件和 REST 响应，不直接访问 C3 WorkflowState、MySQL、Redis 或 Qdrant。
- 前端不能在没有对应 SSE 事件时自行补写业务文本、推导健康安全结论或展示内部数据。
- 当前前端技术栈与 V1 一致：Vue 3 + TypeScript，开发服务器通过 Vite proxy 代理 API 请求。
- 前端展示状态由 SSE 事件驱动——收到什么事件渲染什么内容，不预测、不跳过、不补写。

## 3. 职责

D2 负责：

1. 定义 `AnswerArtifact` 的结构——回答正文、引用证据、用户可见分析摘要；
2. 定义回答内容的允许范围和禁止表述（含具体示例）；
3. 定义用户可见分析摘要的格式——标题、摘要、证据引用（不包含隐藏思维过程）；
4. 定义前端 SSE 事件消费逻辑——事件类型到 UI 状态的映射；
5. 定义前端展示状态机——加载中、阶段分析展示、回答展示、错误、取消；
6. 定义前端组件不做什么——不推导健康安全、不展示内部数据、不补写缺失文本；
7. 定义多人场景下的隐私展示规则——群组视图不区分个人健康原因；
8. 定义前端对 SSE 断连的处理——自动重连、Last-Event-ID 续传、不丢失已展示内容。

## 4. 非职责

D2 不负责：

- 生成回答文本（属于回答模型 + C3 的 `answer_generation` 节点）；
- 传输 SSE 事件（属于 D1）；
- 校验回答的事实正确性（属于 C3 的 `unified_review` 节点和 `atomic_commit` 的前置校验）；
- 定义前端的具体 CSS 样式、组件实现细节或路由结构（属于前端工程实现）；
- 管理用户认证、会话 cookie 或 CSRF 防护（属于基础设施网关层）；
- 实现聊天界面的输入框、消息气泡等通用 UI（属于前端组件库层面）。

## 5. AnswerArtifact 结构

```
AnswerArtifact
├── artifact_id
├── request_id
├── plan_id (所选菜单方案 ID)
├── menu_ref (MenuDecisionArtifact 引用)
├── final_validation_ref (FinalValidationArtifact 引用)
├── content
│   ├── conclusion (结论，1-2 句，放在回答最前面)
│   ├── menu_summary (菜单概述——每道菜的菜名和一句话说明)
│   ├── reasoning_summary (选择依据——为什么选这个方案，引用了哪些已验证事实)
│   ├── health_note (公开健康说明——如"部分候选因与当前健康限制冲突被排除")
│   ├── time_note (时间说明——仅 high 置信度时给出确定值)
│   └── step_highlights (制作要点——关键的步骤顺序或并行建议)
├── user_visible_analysis[] (每个分析阶段的公开摘要)
│   ├── stage
│   ├── title
│   ├── summary
│   └── evidence_refs[]
├── evidence_refs[] (引用的 Artifact 和工具回执 ID)
└── content_hash
```

## 6. 回答内容规则

### 6.1 允许表述

回答可以表述以下内容（前提是对应事实已经过校验）：

- 最终菜单的菜品名称和简要说明；
- "选择了方案X，因为它在满足健康要求的同时更符合你的口味偏好"（软目标比较，不涉及营养数值）；
- "部分候选菜品因与当前健康限制冲突被排除"（不指明具体参与者、疾病或指标）；
- 菜品的大致制作时间（仅 high 置信度时给确定值，中低置信度给范围或"约XX分钟"）；
- "这道菜的主要食材包括：猪肉、青椒、木耳"（来自 B3 公开视图，不修改）；
- 简要的制作顺序和关键步骤（来自 B5 公开视图）。

### 6.2 禁止表述

回答绝对不得出现以下内容：

**营养数值类**：
- "这道菜含钠 800mg"
- "总能量约 450 千卡"
- "蛋白质含量较高"
- 任何 `per_serving` 相关表述

**健康判断类**：
- "这道菜适合高血压患者"
- "因为你的血压偏高，所以..."
- "这些食材对你的糖尿病是安全的"
- 模型自行声明的任何健康安全结论

**疾病与指标类**：
- "考虑到你的高尿酸..."
- "你的血糖指标显示..."
- 任何疾病名称、检测指标值或医学诊断

**隐私侵犯类**：
- "参与者A有花生过敏，所以..."
- "张三不能吃这道菜"
- 任何可以追溯到具体参与者的健康信息

**虚构内容类**：
- 不在最终菜单中的菜品
- 修改后的食材清单（"用鸡胸肉代替了五花肉"——除非这是 B3 中独立的菜品变体）
- 自行估计的制作时间数值（除非来自 B5 的 high 置信度结果）

### 6.3 边界案例处理

| 场景 | 正确表述 | 错误表述 |
|---|---|---|
| 某道菜因过敏被排除 | "部分菜品因与当前健康限制冲突被排除" | "鱼香肉丝因为花生过敏被去掉了" |
| 多人中某人不能吃辣 | "菜单选择了口味适中的方案" | "考虑到参与者B不能吃辣..." |
| 时间不够做某道菜 | "方案Y由于制作时间较长未被选中" | "红烧肉要炖2小时太久了"（如果 2 小时是 low 置信度的估算） |
| 营养目标匹配 | "方案A更符合你的饮食偏好" | "方案A的钠含量更低，适合你的控钠需求" |

## 7. 用户可见分析摘要

每个模型节点可以在 Artifact 中附带 `user_visible_analysis`。它不是模型的隐藏思维过程，而是让用户理解"系统做了什么"的简要说明。

格式：

```
{
  "stage": "query_understanding",
  "title": "理解需求",
  "summary": "你希望一顿三菜一汤的家常午餐，偏好川菜口味，约45分钟完成。",
  "evidence_refs": ["query_plan_artifact_ref"]
}

{
  "stage": "health_evaluation",
  "title": "健康审查",
  "summary": "从符合你口味的候选菜品中，排除了与你当前健康限制冲突的3道菜，剩余17道安全候选。",
  "evidence_refs": ["health_evaluation_receipt_ref"]
}

{
  "stage": "menu_planning",
  "title": "方案设计",
  "summary": "生成了5个可行方案：方案A更注重口味匹配，方案B更注重营养均衡，方案C用时最短。",
  "evidence_refs": ["feasible_menu_artifact_ref"]
}

{
  "stage": "menu_decision",
  "title": "方案选择",
  "summary": "综合考虑你的偏好和时间，选择了方案A——回锅肉、麻婆豆腐、清炒时蔬、紫菜蛋花汤。",
  "evidence_refs": ["menu_decision_artifact_ref"]
}
```

约束：
- 每个 `summary` 不超过 150 字；
- 不暴露疾病名、指标值、营养数值、参与者身份；
- 不包含模型隐藏思维过程、内部评分或"我认为"等主观表达；
- 如果对应阶段的旧分析被修订替代（`analysis_superseded`），前端应替换而非追加显示。

## 8. 前端架构

### 8.1 SSE 事件到 UI 状态映射

前端维护以下展示状态机：

```
状态: idle
  → POST 请求创建成功 → loading

状态: loading
  → 收到 request_accepted → 显示"正在理解需求..."
  → 收到 analysis_ready (query_understanding) → 显示"需求分析"摘要
  → 收到 analysis_ready (health_evaluation) → 显示"健康审查"摘要
  → 收到 analysis_ready (menu_planning) → 显示"方案设计"摘要
  → 收到 analysis_ready (menu_decision) → 显示"方案选择"摘要
  → 收到 answer_ready → 显示完整回答 → streaming_answer
  → 收到 error → 显示错误信息 → error

状态: streaming_answer
  → 收到 result_committed → 显示"推荐完成" → complete

状态: complete
  → 用户可查看完整菜单、修改/替换菜品、发起新请求

状态: error
  → 显示错误类型和可操作提示
  → needs_clarification → 显示需要用户确认的问题
  → no_safe_menu / no_feasible_menu → 显示原因和可选操作
  → failed / cancelled → 显示错误码和重试入口
```

### 8.2 前端组件

前端按以下功能域分组（与 V1 结构对齐但按 V2 事件流调整）：

| 功能域 | 核心组件 | 消费数据 |
|---|---|---|
| 聊天 | `ChatPanel`、`MessageBubble`、`StageIndicator` | SSE 事件 → 阶段分析 + 回答文本 |
| 参与者 | `ParticipantSelector`、`ParticipantBadge` | D1 `POST /sessions` 的参与者列表 |
| 推荐结果 | `MenuCard`、`DishDetail`、`TimeEstimate` | `answer_ready` 中的 `menu_summary` + `time_note` |
| 健康说明 | `HealthNote`（只读展示，不渲染数值） | `answer_ready` 中的 `health_note` |

不再保留"营养"展示分组（V1 可能有），因为营养数据不再进入回答和前端。

### 8.3 SSE 连接管理

```
前端 EventSource 连接:
→ 连接 /v1/recommendation-requests/{request_id}/events
→ 收到事件 → 按 event_type 分发到对应 UI 状态更新
→ 连接断开 → 自动重连（携带 Last-Event-ID）
→ 重连成功 → 从事件游标继续消费（不丢失已展示内容）
→ 重连失败（3次后）→ 降级为 GET 状态查询轮询（每 5 秒）
→ 收到 result_committed 或 error → 关闭 EventSource
```

前端不因 SSE 断开而重新创建请求。连接管理逻辑封装在 `useSSEStream` composable 中。

## 9. 前端禁止行为

### 9.1 不推导健康安全

- 前端不能根据展示的菜品食材反向推断用户的健康状态；
- 不能在前端显示"回锅肉不含过敏原"（即使菜品确实通过了健康审查——这个结论必须来自服务器）；
- 不能在 UI 中分类"安全""不安全"标签。

### 9.2 不展示内部数据

- 不在前端渲染营养数值、`per_serving`、采购量；
- 不在前端渲染模型隐藏思维过程或 C3 内部计数器；
- 不在前端渲染 B4 健康命中路径、约束代码或覆盖状态；
- 如果 `answer_ready` payload 意外包含禁止字段（D1 扫描漏了），前端应过滤而非直接渲染。

### 9.3 不补写缺失内容

- `error` 事件到达时 → 展示错误信息，不生成假回答；
- `answer_ready` 未到达但 SSE 断开 → 显示"连接中断，正在重连"，不自行写出菜单；
- 阶段事件缺失某 stage → 不跳过该 stage 的 UI 卡片，显示空白占位。

### 9.4 不暴露其他参与者

- 多人场景下，`health_note` 是群组级匿名说明——前端不能额外渲染"具体是谁不能吃"；
- 聊天界面中不显示参与者的 `user_id` 或真实姓名，只显示 `participant_ref` 的匿名标签（如"参与者A"）。

## 10. 替换与恢复交互

用户对当前菜单不满意时，前端提供替换和恢复入口（不新增独立的菜单编辑功能）：

- 替换：用户选择一道菜 → 前端发起新请求（携带 `action=replace` 和 `target_recipe_id`）→ 服务端重新走完整健康审查和工作流；
- 恢复：用户从菜单历史中选择旧版本 → 前端发起新请求（携带 `action=restore` 和 `plan_id`）→ 服务端重新执行健康校验后恢复。

替换和恢复都是新请求（有新的 `request_id`），不是就地修改当前菜单。前端在收到新请求的 `answer_ready` 后更新展示。

## 11. 依赖方向

允许依赖：

```
回答模型 → B3 PublicRecipeView (公开菜品信息)
回答模型 → B5 PublicTimeSummary (公开时间说明)
回答模型 → MenuDecisionArtifact (由 C3 提供)
回答模型 → FinalValidationArtifact (由 C3 提供)
前端 → D1 SSE 事件流
前端 → D1 REST API (请求创建、状态查询、取消、会话管理)
前端 → D2 组件类型定义 (AnswerArtifact 等 Schema 的 TypeScript 类型)
```

禁止依赖：

```
回答模型 → B2/B4/B6 任何内部接口
回答模型 → MySQL/Qdrant/Redis
前端 → C3 WorkflowState 内部结构
前端 → MySQL/Qdrant/Redis
前端 → B2/B3/B4/B5/B6 任何领域服务
前端 → 内部营养数值、健康档案原文
```

## 12. 测试和验收标准

### 12.1 回答内容

- 回答所列的每道菜均在 `MenuDecisionArtifact` 所选菜单中；
- 回答不包括 `MenuDecisionArtifact` 未选的菜品；
- 回答不含营养数值（`mg`、`kcal`、`g` 等单位前后没有数字）；
- 回答不含疾病名称（如"糖尿病""高血压""过敏"）；
- 回答不含原始指标值（如"血压 150/95"）；
- 回答不含参与者真实身份；
- `health_note` 不具体指明哪道菜因什么健康原因被排除。

### 12.2 用户可见分析

- 每个阶段的 `summary` ≤ 150 字；
- 不含"我认为""系统判断"等主观表述；
- 不含营养数值、疾病名、指标值；
- `evidence_refs` 中每个引用真实存在。

### 12.3 前端展示状态

- 请求创建后显示加载状态；
- 按 `analysis_ready` 事件顺序依次展示阶段卡片；
- `answer_ready` 到达后渲染完整回答；
- `result_committed` 到达后显示完成状态；
- `error` 到达后显示对应错误信息（不生成假回答）；
- `clarification_needed` 到达后显示需要用户确认的问题。

### 12.4 SSE 断连恢复

- 断连后自动重连；
- 重连后通过 `Last-Event-ID` 续传，不丢失事件；
- 连续 3 次重连失败后降级为轮询；
- 轮询期间不重复展示已有事件。

### 12.5 隐私

- 多人场景聊天界面不显示具体参与者的健康原因；
- 前端不渲染 `user_id` 或真实姓名；
- 前端不渲染内部营养值（即使 payload 意外包含）。

### 12.6 替换与恢复

- 替换请求创建新的 `request_id`；
- 恢复请求重新执行健康校验；
- 前端不提供"直接编辑食材"的入口。

## 13. 旧实现与目标实现差异

| 维度 | 旧实现 | V2 目标 |
|---|---|---|
| 回答内容 | 可能包含营养值、健康标签 | 严格限制，不含数值和疾病名 |
| 用户可见分析 | 可能不明确或缺失 | 每阶段 ≤150 字结构化摘要 |
| 前端展示分组 | 可能有"营养"分组 | 移除营养分组 |
| 前端健康展示 | 可能展示"安全""含过敏原" | 不展示健康判定标签 |
| 替换/恢复 | 存在但不一定重新校验 | 每次替换/恢复必重新走健康校验 |
| SSE 断连处理 | 可能不完善 | 明确重连 + Last-Event-ID + 降级 |

## 14. 迁移分类

| 旧实现 | 分类 | 处理结论 |
|---|---|---|
| 回答模型提示词 | `REWRITE` | 按 D2 回答内容规则重写提示词，明确禁止表述和边界案例 |
| `frontend/src/features/` 聊天和推荐组件 | `REFACTOR` | 保留 Vue 3 组件结构；按 V2 事件流重写状态管理；移除营养展示组件 |
| `frontend/src/features/` 营养展示 | `REMOVE` | 营养数据不再进入前端 |
| 前端 SSE 消费逻辑 | `REFACTOR` | 保留 EventSource 机制；按 V2 事件类型重写事件分发 |
| 旧回答相关测试 | `REWRITE` | 按禁止表述列表重写；增加边界案例测试 |

## 15. 审查后清理项

以下内容在 D1、D2 和 C3 全部迁移并通过验收后清理：

- 旧回答提示词中的营养数值、健康标签、疾病描述模板；
- 前端营养展示组件和对应的 API 类型；
- 前端健康标签渲染逻辑（"适合""不适合""含过敏原"等）；
- 已由新 D2 规则替代且确认无消费者的旧回答 Schema 字段。

## 16. 与全局流程和后续模块的关系

```
C3 answer_generation 节点 → 回答模型（遵守 D2 内容规则）
C3 unified_review 节点 → 审查回答是否符合 D2 规则
D1 SSE → 前端（按 D2 事件映射更新 UI）
前端 → D1 REST (替换/恢复创建新请求)
D3 测试 → D2 回答规则和前端展示验收
```

- D1 负责传输，D2 负责定义传输的内容应该是什么、不应该是什么；
- C3 的 `unified_review` 节点以 D2 规则作为审查依据之一；
- D3 的端到端验收引用 D2 的禁止表述列表作为检查点。

## 17. 待考量事项

以下问题不影响当前设计通过，但在进入实现阶段前需要进一步确认。在此留痕供后续回顾。

### 17.1 回答模型的提示词工程

D2 定义了回答能说什么、不能说什么，但提示词如何将规则翻译为模型可遵循的指令，是基础设施适配器层面的工程问题。特别是"边界案例"（如用户追问"为什么排除鱼香肉丝"），模型需要在拒绝暴露隐私和保持有用性之间平衡。

**建议**：实现阶段为每个禁止表述类别编写正反例，放入回答模型的提示词。边界案例作为单独的 few-shot 示例集维护。在 D3 测试中专门覆盖用户追问健康原因的场景。

### 17.2 前端的阶段分析卡片逐步展示 vs 一次性展示

当前设计是"收到 `analysis_ready` 事件 → 展示对应阶段的卡片"。四个阶段的事件通常在几百毫秒到几秒内依次到达，卡片逐个出现可能造成 UI 闪烁。另一种做法是缓冲所有阶段事件，一次性渲染完整的分析流程。

**建议**：实现阶段两种都试一下。如果事件间隔太短（< 200ms），合并渲染；如果间隔长（健康审查耗时明显），逐步展示给用户感知到"系统正在工作"。这个行为作为前端配置项保留。
