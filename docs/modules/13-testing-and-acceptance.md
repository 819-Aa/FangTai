# V2 测试与验收模块设计

- 状态：`APPROVED`
- 日期：2026-08-09
- 适用项目：`program_v2`
- 上游依据：[系统总体设计](../00-system-overview.md)、[全局不变量](../contracts/global-invariants.md)、[模块边界](../contracts/module-boundaries.md)、全部 B/C/D 阶段已批准模块

## 0. 2026-08-09 批准的实现基线

- 建立 `INV-001..INV-024 -> 校验点 -> 测试 ID -> 证据文件` 追踪矩阵；没有自动化或真实集成证据的不变量视为未验收。
- pytest collect、全量非 live、真实 MySQL/Qdrant/Redis 集成、模型 live 契约、API/SSE、前端单测/构建、静态检查和 2,000 条数据门禁分别报告，不能用其中一类替代另一类。
- 基础设施未启动造成的 skip 只能记为 `NOT_RUN`，不能计入通过率或 production-ready 证据；mock E2E 只能证明编排接口，不证明全链路。
- 每个 DeepSeek 任务先证明红测试因目标缺失而失败，再实现、局部验证、全局校准和独立只读验收；锁定测试和验收脚本不在任务白名单。
- 所有验证保存命令、工作目录、时间、退出码、stdout/stderr 散列和 diff；文字自报“通过”无效。
- 最终验收必须从全新固定数据 staging 开始，真实初始化并通过匿名前端请求，直至 post-commit SSE、状态查询、数据库结果、健康审计和会话事实一致。

## 1. 模块目的

D3 定义 V2 系统的完整验证策略。它不写测试代码，而是规定每个模块必须覆盖哪些测试、各层测试的职责边界、跨模块场景的验证要求，以及 V2 通过全链路验收并替代旧系统的最终条件。

D3 是所有模块自身"测试和验收标准"小节的汇总和交叉索引——如果某个模块的测试要求只在 D3 中出现而未写回该模块，就是遗漏。

## 2. 已确认前提

- 自动化测试是核心建设项，不与 LangSmith、Trace 详情页或指标平台等延期能力绑定（系统总览 §23）。
- 全局不变量（INV-001 ~ INV-024）全部必须通过自动化验证——这是 V2 退出旧项目的硬性条件之一（ADR-0001）。
- 测试不替代生产校验——C3 的运行时校验（必需工具回执、Artifact Schema、证据引用）是独立的防线。
- 测试使用项目已有的 Python 测试框架（pytest）和前端测试框架（Vitest + Vue Test Utils），不引入新的测试平台。
- 测试数据使用项目内固定数据（2,000 条菜品、50 份健康档案、固定对话用例），不依赖外部网络或实时数据源。
- 端到端测试依赖 MySQL、Qdrant 和本地 BGE 模型——需要在这些服务可用时运行。

## 3. 职责

D3 负责：

1. 定义测试分层及各层的职责边界；
2. 汇总每个模块（B1-B6、C1-C4、D1-D2）的必测项；
3. 定义跨模块场景测试——验证模块组合后的完整行为；
4. 定义全局不变量验证——每条 INV 在哪个测试层、用什么方式验证；
5. 定义数据质量门禁——离线构建产物必须通过的自动化检查；
6. 定义回归测试策略——旧实现中有价值的案例如何保留；
7. 定义 V2 全链路验收条件——所有条件都满足才算"V2 可以替代旧系统"。

## 4. 非职责

D3 不负责：

- 编写具体测试代码（属于各模块的实现阶段）；
- 配置 CI/CD 流水线（属于工程基础设施，D3 定义触发条件和通过标准）；
- 管理测试数据集的版本或生成新的测试用例数据（使用项目内已有数据）；
- 替代 C3 的运行时校验、D1 的响应字段扫描或 D2 的前端过滤；
- 定义模型的评估基准或进行模型效果对比。

## 5. 测试分层

| 层级 | 范围 | 框架 | 运行条件 | 覆盖率要求 |
|---|---|---|---|---|
| 单元测试 | 单个函数或类的输入输出 | pytest | 无外部依赖 | 核心算法路径 100% |
| 契约测试 | 模块间公开接口的输入输出 | pytest | 无外部依赖（mock 对方） | 每个公开接口至少 1 个正向 + 1 个失败用例 |
| 集成测试 | 模块 + 真实基础设施 | pytest + Docker | MySQL、Qdrant、Redis 可用 | 每个模块的数据读写路径 |
| 场景测试 | 多模块组合的端到端行为 | pytest + Docker | 全部服务可用 + 本地模型 | 关键场景全部覆盖 |
| 端到端测试 | 从 API 到回答的完整链路 | pytest + Docker | 全部服务可用 + 本地模型 | 覆盖所有终态路径 |

前端测试使用 Vitest（单元/组件）和 Playwright 或等效方案（端到端），分层与后端对齐。

### 6.9 C3 Agent 工作流

| 测试项 | 层级 | 关键断言 |
|---|---|---|
| 正常链路（单人） | 场景 | accepted→running→completed，全部 Artifact 链完整 |
| 正常链路（多人） | 场景 | 全员交集正确执行 |
| 必需工具漏调 | 场景 | 每个角色漏调其必需工具→`REQUIRED_TOOL_NOT_CALLED`→`failed` |
| 越权工具调用 | 场景 | 查询理解调 B4→`TOOL_PERMISSION_DENIED`；回答调 B4→`TOOL_PERMISSION_DENIED` |
| 扩展召回上限 | 场景 | 第二次调用→`WORKFLOW_RETRY_LIMIT_EXCEEDED` |
| 最终校验回流 | 场景 | EXCLUDE→replan(1次)→再 EXCLUDE→`FINAL_HEALTH_VALIDATION_FAILED` |
| 审查修订上限 | 场景 | 修订→复审→再 REVISION_REQUIRED→`WORKFLOW_RETRY_LIMIT_EXCEEDED` |
| 终态正确性 | 场景 | `no_safe_menu`≠`no_feasible_menu`≠`failed` |
| 幂等 | 场景 | 同键同载荷→已有结果；同键不同载荷→409 |
| 取消 | 场景 | 取消在节点边界生效；已提交不可改为 cancelled |
| SSE 断连 | 场景 | 断连不取消、不重跑、不重复请求 |
| 原子提交回滚 | 场景 | 审计失败→回滚→不留 `completed` |

| 前端 SSE 断连恢复 | 端到端 | 重连+Last-Event-ID+降级轮询 |
| 替换/恢复 | 端到端 | 新 request_id+重新健康校验 |

## 7. 跨模块场景测试

以下场景涉及 3 个以上模块协作，必须通过后才能进入全链路验收：

| 场景 | 涉及模块 | 验证内容 |

## 12. V2 全链路验收条件

以下条件全部满足后，V2 才被认为通过验收，可以进入旧项目退出审查（ADR-0001）：

1. 全部 18 条全局不变量通过自动化验证；
2. 所有 12 个模块的必测项通过；
3. 全部 10 个跨模块场景测试通过；
4. 全部数据质量门禁通过；
5. 食材健康硬筛选回归案例全部通过（正反例，含可选/替代/复合组成）；
6. 五模型工作流 + 全部工具权限完整运行（单人 + 多人各 ≥20 次无失败）；
7. 多人健康交集场景通过（≥3 种参与者组合）；
8. 多轮对话上下文场景通过（≥10 轮无约束丢失或上下文损坏）；
9. API/SSE/前端全链路通过（正常链路 + 全部终态路径）；
10. 新旧关键场景对照完成（V2 的推荐结果与 V1 在相同输入下的差异有合理解释）；
11. 不存在依赖旧项目的消费者或在途请求。

验收不通过百分比或"基本完成"衡量——每个条件只有通过/未通过。

## 13. 依赖方向

D3 是所有模块的验证者，只依赖各模块的公开接口和 Schema。D3 不能被任何业务模块依赖——测试不能成为生产代码的运行时依赖。

## 14. 与全局流程和后续模块的关系

```
D3 验证 ← 全部 B/C/D 阶段模块
D3 验收条件 ← ADR-0001 旧项目退出条件
D4 迁移与清理 ← D3 全链路验收通过后执行
```

- D3 汇总各模块的"测试和验收标准"小节，定义跨模块覆盖；
- D3 的验收条件是 D4 迁移与清理的前置条件；
- D3 自身不包含被测试的代码——它是对测试的要求，不是测试本身。
