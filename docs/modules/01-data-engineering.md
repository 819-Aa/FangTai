# V2数据工程模块设计

- 状态：`APPROVED`
- 日期：2026-08-04
- 适用项目：`program_v2`
- 上游依据：[系统总体设计](../00-system-overview.md)、[全局不变量](../contracts/global-invariants.md)、[模块边界](../contracts/module-boundaries.md)

## 1. 模块目的

数据工程模块把项目中已经确定的菜品、用户健康档案、营养参考和验收数据处理成系统可以安全读取的结构化事实。原始数据固定不代表可以直接使用；用户健康审查、RAG召回、营养软排序、时间规划和Agent工具都必须消费经过清洗、标准化、关系构建和质量验证的产物。

本模块定义整条离线流水线、各类产物之间的连接方式、质量门禁和旧实现迁移边界。用户健康、食材、健康规则、时间和营养的具体算法分别在后续模块文档中展开，本模块负责保证它们在同一数据链路中协作，而不是形成彼此孤立的数据集。

## 2. 已确认前提

- 项目已有菜品和用户健康档案是确定的数据，不在V2中扩展到新的现实世界数据。
- 项目已有营养参考文件作为固定参考输入；数据来源获取和更新不属于本模块。
- 所有固定输入仍须经过V2自己的处理逻辑，不能直接复制旧系统派生产物作为新系统事实。
- 处理逻辑在V2开发期间发生变化时执行完整离线重建；正式运行期间不更新固定业务数据。
- 不设计增量同步、多数据版本共存或运行时数据切换。
- 固定业务数据表和菜品检索索引运行时只读；请求、会话、菜单结果和健康审计等运行数据不属于固定数据。
- 数据处理结论服从全局健康边界：食材健康硬关系负责排除，营养只负责安全候选之间的软排序。

## 3. 职责

数据工程负责：

1. 校验固定原始文件的结构、主键、必要字段和记录范围；
2. 清洗并标准化用户健康档案，不推测缺失事实；
3. 清洗菜品记录，保留稳定`recipe_id`和原始字段；
4. 拆分食材文本，建立标准`ingredient_id`、别名和菜品食材关系；
5. 区分可食食材、非食用材料、复合调味品和非菜品记录；
6. 为健康规则准备标准健康约束代码和食材健康关系数据；
7. 保留原始制作步骤并派生结构化步骤、任务、时间、设备和依赖；
8. 匹配固定营养参考，生成只供内部软排序使用的营养特征和置信度；
9. 生成MySQL固定业务数据初始化产物；
10. 生成RAG菜品文档和Qdrant索引输入；
11. 执行单阶段质量校验、跨产物一致性校验和固定验收案例；
12. 输出可诊断的质量报告，失败时停止完整构建。

## 4. 非职责

数据工程不负责：

- 获取、爬取、购买或更新外部数据；
- 在线解析原始CSV、JSON或用户健康档案原文；
- 根据具体用户直接决定一道菜是否安全；
- 让RAG文档携带或推断健康`PASS`；
- 生成医疗诊断、治疗建议或真实世界人群结论；
- 计算烹饪营养损耗；
- 计算或展示`per_serving`、个人摄入量、人数份量和采购量；
- 为缺失的食材数量、健康指标、步骤或时间编造精确值；
- 处理在线会话、WorkflowState、菜单选择和最终回答；
- 管理运行时数据发布、数据版本切换或多套数据共存。

## 5. 上游输入

| 输入类别 | 当前项目内容 | 使用原则 |
|---|---|---|
| 菜品原始数据 | 2,000条菜谱记录 | 只读；保留原始顺序和稳定ID |
| 用户健康档案 | 50份详细健康档案 | 只读；缺失指标保持`null` |
| 营养参考 | 项目内食物成分参考文件 | 只读；不在默认流水线中联网更新 |
| 对话与检索验收数据 | 固定对话用例和期望 | 只用于质量门禁，不作为生产事实 |
| 构建配置 | 别名、分类、规则和Schema配置 | 必须可审查，不能隐藏在单个巨型代码文件中 |

输入路径属于部署配置，数据工程只要求它们可读，不承担输入来源管理。旧项目生成的`cleaned`、`profiles`、`database`和`knowledge_base`只能用于对照，V2必须重新生成自己的派生产物。

## 6. 下游输出

### 6.1 结构化固定事实

- 标准化用户档案；
- 原始健康事实和可供规则模块解释的标准字段；
- 菜品、菜品变体和菜品类型；
- 标准食材、审核别名和食材分类；
- 菜品—食材关系；
- 食材—健康约束关系；
- 原始步骤和结构化步骤任务；
- 菜品时间画像；
- 食材营养匹配和菜品营养软特征。

### 6.2 存储初始化产物

- MySQL固定业务表初始化数据；
- RAG菜品检索文档；
- Qdrant向量索引输入及必要payload；
- 数据质量、检索质量和跨产物一致性报告。

这些产物使用稳定领域ID连接。下游模块通过Repository或领域服务读取，Agent节点不能直接读取生成文件。

## 7. 数据分层与所有权

```text
固定原始输入
→ 清洗层
→ 标准事实层
→ 关系与派生特征层
→ MySQL/RAG/Qdrant初始化层
→ 质量报告层
```

| 分层 | 典型内容 | 运行时是否直接读取 |
|---|---|---|
| 原始输入 | 原始菜品、原始用户档案、营养参考 | 否 |
| 清洗层 | 字段规范化、保留原文的清洗记录 | 否 |
| 标准事实层 | 用户事实、菜品、食材、步骤 | 通过MySQL领域接口读取 |
| 关系与特征层 | 食材关系、健康关系、时间画像、营养软特征 | 通过对应领域服务读取 |
| 检索层 | RAG文档、Qdrant payload和向量 | 仅由RAG服务读取 |
| 报告层 | 质量结果、错误明细、覆盖情况 | 仅用于构建和验收 |

数据工程拥有离线产物的生成责任；运行时各领域模块拥有对应业务事实的查询接口。数据工程不能越过领域服务参与在线判断。

## 8. 核心处理流程

```text
1. 输入结构校验
2. 用户健康档案标准化
3. 菜品记录清洗与类型识别
4. 食材解析、标准化与关系构建
5. 食材健康关系准备和校验
6. 步骤、任务、设备与时间处理
7. 营养参考匹配和软特征构建
8. 跨数据域连接校验
9. 生成MySQL初始化数据
10. 生成RAG文档和Qdrant索引输入
11. 执行数据、健康边界和检索质量门禁
12. 验证通过后形成正式生成产物
```

每一阶段只读取已经通过上游校验的产物。任一必需阶段失败时，后续阶段不执行，未完成产物不能进入在线系统。

## 9. 各维度处理及其全局连接

### 9.1 用户健康档案

用户档案处理分开保存以下语义：

- 身份引用：稳定用户ID，Agent侧只投影匿名`participant_ref`；
- 原始健康事实：疾病或特殊人群、过敏、体检指标；
- 普通偏好：口味和正向饮食偏好；
- 健康目标：控糖、控钠等目标表达，不直接等同于食材硬禁忌；
- 数据质量：字段是否存在、格式是否有效、是否与源值一致。

缺失指标保持`null`，不根据年龄、疾病名称、其他指标或模型推断补值。数据工程只把原始事实标准化；哪些事实形成有效健康约束，由用户健康档案模块和确定性规则解释。

### 9.2 菜品与食材

菜品保留稳定`recipe_id`，同名菜品通过变体标识区分，不按名称合并。记录必须区分：

- 可推荐菜品；
- 调味酱、馅料等准备项；
- 料理程序或设备测试记录；
- 已组合菜单；
- 其他不可作为独立菜品推荐的记录。

食材处理遵循：

- 原始食材文本必须保留；
- 数量和单位可以解析用于内部营养估算，但不生成份量和采购量；
- 无法确认的数量保持未知，不自动补齐；
- 别名必须映射到稳定`ingredient_id`；
- 可选和替代食材必须拆成独立食材关系，健康审查对全部成员取并集，不能自动选择安全分支；
- 非食用材料不能进入营养或健康食材判断；
- 复合调味品只能按已有、经过确认的组成关系展开；
- 禁止使用宽泛字符串包含推断食材身份。

### 9.3 食材与用户健康的关联

系统不直接维护“用户—菜品是否安全”的静态结论，而是通过两段确定性关系在请求时连接：

```text
用户原始健康事实
→ 有效健康约束代码
→ 审核通过的食材健康关系
→ 标准ingredient_id
→ recipe_id包含的标准食材
→ 菜品健康评估结果
```

食材健康关系至少区分过敏、疾病、异常指标派生约束和明确禁忌。只有绑定标准食材且允许参与硬筛选的关系才能排除菜品。字符串包含、未经确认的类别推断、营养估算和RAG相似度都不能生成硬命中。

一道菜的任一标准食材命中任一参与者的有效健康硬约束时，整道菜排除。多人菜单对所有参与者执行同一规则并取全员安全交集。

### 9.4 制作步骤与时间

原始步骤逐条保留，结构化处理只提取可验证事实：

- 步骤顺序和依赖；
- 主动操作；
- 设备占用；
- 被动等待；
- 明确时长、时长范围和未知时长；
- 步骤涉及的标准食材；
- 时间来源和置信度。

缺失步骤不自动编造，无法解析的时间保持未知。整套菜单时间由后续时间模块基于任务图计算；同一烹饪者的主动操作互斥，相同设备互斥，不同设备和被动等待在依赖允许时并行。

严格时间限制只使用高置信度时间上界。中低置信度时间可以参与软排序，但不能把菜品判定为严格满足时限。

### 9.5 营养数据

营养匹配按以下顺序进行：

1. 标准食材与固定营养参考精确匹配；
2. 通过审核别名匹配到同一食材；
3. 使用可解释的同类或近似食材参考进行估算；
4. 无合理参考时保持未知。

每条匹配保留来源食材、匹配方法、置信度和已知数量覆盖情况。菜品营养特征基于原始食材理论值形成内部比较特征，不计算烹饪损耗，也不生成`per_serving`或个人摄入量。

官方参考中缺失的数据允许做受控估算，因为它只用于健康安全菜品之间的辅助排序。估算值无论置信度高低都不能触发健康硬筛选；置信度越低，对软评分的影响越受限。具体营养值和置信度不进入正常回答和前端。

### 9.6 RAG文档与Qdrant索引

RAG文档由验证通过的可推荐菜品生成，包含：

- `recipe_id`；
- 菜名、菜品类型和正向描述；
- 标准食材名称；
- 口味、菜系、烹饪方式等检索字段；
- 步骤摘要和可用时间字段；
- Qdrant过滤所需的非健康元数据。

RAG文档不包含用户健康档案、健康`PASS`、食材健康硬关系、内部营养数值或医疗效果。Qdrant只建立菜品召回索引；健康审查在召回之后由健康工具完成。

## 10. 跨维度一致性规则

- 用户、菜品和食材必须使用稳定ID，不能由下游按名称重新建立身份。
- 每个可推荐菜品必须能够展开到标准食材集合。
- 健康评估必须引用与菜品事实相同的`recipe_id`和`ingredient_id`。
- 营养和时间只附着于已有标准菜品，不产生新菜品或修改食材。
- RAG文档中的`recipe_id`必须存在于菜品目录，并且只覆盖可推荐菜品。
- RAG候选经过健康审查后才能进入菜单规划；营养和时间只能比较健康安全候选。
- 回答和前端只能读取最终已验证菜单，不直接读取数据工程中间产物。

## 11. 构建接口

数据工程只提供离线接口，不提供Agent工具：

```text
validate_inputs()
build_user_profiles()
build_recipe_catalog()
build_ingredient_relations()
build_health_relation_data()
build_step_time_profiles()
build_nutrition_features()
validate_cross_domain_links()
build_mysql_seed()
build_rag_documents()
build_vector_index()
run_quality_gates()
rebuild_all()
```

具体函数签名以实现阶段的可执行契约为准。完整构建入口按固定顺序调用各阶段，不在同一个巨型模块中重新实现具体算法。

## 12. 依赖方向

```text
固定输入读取器
→ 各数据域标准化器
→ 共享领域Schema
→ 关系和派生特征构建器
→ 存储初始化适配器
→ 质量门禁
```

- 数据工程可以依赖领域Schema和Repository初始化接口。
- 数据工程不能依赖Agent节点、WorkflowState、API Schema或前端类型。
- RAG文档构建只能读取菜品目录的公开构建视图，不能导入健康评估实现。
- 营养、时间和健康关系构建不能互相改写标准食材身份。
- 基础设施加载器负责写入MySQL和Qdrant，数据处理算法不直接决定在线业务状态。

## 13. 异常与停止条件

| 错误码 | 触发条件 | 处理 |
|---|---|---|
| `SOURCE_DATA_INVALID` | 固定输入缺失、结构错误、主键重复或必要字段不可解析 | 停止 |
| `USER_PROFILE_NORMALIZATION_FAILED` | 健康事实无法保持原义地标准化 | 停止用户档案阶段 |
| `RECIPE_NORMALIZATION_FAILED` | 菜品ID、类型或必要文本处理失败 | 停止菜品阶段 |
| `INGREDIENT_NORMALIZATION_FAILED` | 可推荐菜品无法形成标准食材集合 | 停止食材阶段 |
| `UNAPPROVED_HEALTH_RELATION` | 未满足硬关系条件的数据试图进入健康硬筛选 | 停止健康关系构建 |
| `STEP_STRUCTURE_INVALID` | 必需步骤顺序或关键引用无法验证 | 标记不可执行；达到门禁阈值时停止 |
| `NUTRITION_MATCH_INVALID` | 营养匹配来源或方法不可解释 | 丢弃该匹配并降为未知；结构性问题时停止 |
| `CROSS_DOMAIN_REFERENCE_FAILED` | 用户、菜品、食材、步骤、营养或RAG引用不存在 | 停止 |
| `DATABASE_INITIALIZATION_FAILED` | MySQL固定业务数据初始化失败 | 停止 |
| `VECTOR_INDEX_BUILD_FAILED` | Qdrant索引构建或最小检索验证失败 | 停止 |
| `DATA_PIPELINE_VALIDATION_FAILED` | 任一强制质量门禁未通过 | 整体构建失败 |

构建失败不自动重试，也不继续使用部分新产物。修正处理逻辑后由开发者显式重新执行完整构建。

## 14. 构建与初始化要求

- 固定原始输入保持只读，流水线不得覆盖。
- V2派生产物写入V2自己的生成目录，不覆盖旧项目产物。
- 单阶段产物必须先通过本阶段Schema和质量校验，才能交给下游。
- 正式生成目录只接收完整构建并通过全部质量门禁的产物。
- MySQL初始化和Qdrant索引构建使用V2独立的数据库和Collection，不修改旧系统运行数据。
- 不维护活动数据版本或多套在线数据。
- 正式运行期间不执行数据重建命令。

## 15. 质量门禁与验收标准

### 15.1 输入与身份

- 2,000条菜品全部保留稳定`recipe_id`，不能因清洗重排ID；
- 50份用户档案全部保留稳定用户ID；
- 同名菜品保留为不同变体；
- 原始文本在标准化后仍可追溯。

### 15.2 用户健康档案

- 缺失健康指标保持`null`；
- 血压、孕周和数值指标使用严格解析；
- 疾病、过敏、健康目标和口味偏好不混为同一类约束；
- 标准化过程不生成原始档案中不存在的健康事实。

### 15.3 菜品与食材

- 每个可推荐菜品至少拥有一个标准可食食材；
- 数量或单位后缀不得泄漏到食材身份；
- 水、全蛋液等审核别名映射稳定；
- 非食用材料不进入营养和健康判断；
- “海鲜菇”“蟹味菇”“红酒醋”“素蚝油”等名称不得因字符串包含产生错误硬关系；
- 非菜品、料理程序、组合菜单和测试记录不能进入RAG推荐集合。

### 15.4 健康关系

- 每条硬关系都绑定标准食材、约束代码和明确证据；
- 未确认关系不能触发硬排除；
- 营养值、营养标签和RAG分数不能出现在健康硬关系输入中；
- 多人场景能够通过统一关系链得到全员安全交集。

### 15.5 步骤与时间

- 原始步骤和结构化步骤可以逐条对应；
- 不自动补写原始数据中不存在的制作步骤；
- 未知时长保持未知并降低置信度；
- 严格时间过滤不会接受中低置信度结果；
- 设备和依赖信息能够支持后续菜单任务图调度。

### 15.6 营养

- 每条营养匹配都有来源、方法和置信度；
- 短别名不得错误命中无关食材；
- 官方参考缺失时的估算只能产生软特征；
- 不生成烹饪损耗、`per_serving`、个人摄入或采购量；
- RAG文档、回答Schema和前端Schema不包含内部营养数值。

### 15.7 RAG与跨产物

- RAG文档`recipe_id`与可推荐菜品集合完全对应；
- MySQL菜品、食材关系、营养、步骤和RAG文档不存在悬空引用；
- RAG文档保留完整可用的检索文本和步骤摘要；
- Qdrant最小检索测试能够返回真实`recipe_id`；
- RAG产物不携带健康安全结论。

## 17. 审查后清理项

以下内容只有在V2对应消费者全部迁移并通过验收后才能删除：

- 旧的`per_serving`、菜品份量、采购量和烹饪损耗字段及计算代码；
- `catalog.py`中已经被新模块替代的混合常量和辅助函数；
- RAG中的健康风险判定或用户健康过滤逻辑；
- 自动补写缺失步骤的逻辑和对应测试；
- 默认流水线中的营养来源抓取逻辑；
- 无消费者的旧Manifest、压缩包和重复生成产物；
- 新系统已经不再读取的旧数据表、索引字段和兼容适配器。

清理前必须使用代码引用、测试和运行配置确认没有消费者。清理属于后续受控变更，不在本设计文档编写阶段执行。
