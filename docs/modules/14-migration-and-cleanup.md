# V2 迁移与清理模块设计

- 状态：`APPROVED`
- 日期：2026-08-09
- 适用项目：`program_v2`
- 上游依据：[系统总体设计](../00-system-overview.md)、[架构决策 ADR-0001](../decisions/0001-v2-workspace-and-migration.md)、[ADR-0004](../decisions/0004-fixed-source-and-one-time-identity-rebuild.md)、[测试与验收模块](13-testing-and-acceptance.md)、全部 B/C/D 阶段模块的迁移分类和清理项

## 0. 2026-08-09 批准的实现基线

- 旧 `program` 全程只读，可借鉴解析候选、异常样本和测试，但不能修改，也不能把旧派生数据直接认定为 V2 权威事实。
- 已授权对空 V2 环境执行一次性全量食材身份重建；旧 V2 食材 ID 不要求保留，必须产出旧/现状到新 ID 的 merge/split/discard crosswalk 和差异报告。
- 删除或覆盖任何已存在 V2 数据前仍需精确目标、备份/可恢复方案和人工授权；DeepSeek 无权自行执行生产破坏性操作。
- `program_v2` 自身 Git 元数据无效时整个执行停在 `BLOCKED_GIT_METADATA`；所有 Git 命令必须以 `program_v2` 为仓库根，不受外层 `竞赛/.git` 影响。禁止 `git init`、覆盖 `.git` 或在无基线状态清理文件。
- 切换条件是 INV-001..INV-024、固定数据门禁、真实基础设施前后端全链路和失败路径全部通过，不以“代码写完”或 mock 测试通过代替。
- 最终切换仍不自动删除 V1；V1 退出是后续独立受控变更。

## 1. 模块目的

D4 定义从旧系统 `program` 到新系统 `program_v2` 的完整迁移路径：实现顺序、每模块的迁移分类、新旧系统隔离规则、清理旧代码和旧数据的前置条件，以及旧项目最终退出的硬性条件。

D4 不执行迁移——它只定义什么时候可以迁、怎么迁、迁完后什么可以删。

## 2. 已确认前提

- 旧系统 `program` 在 V2 全链路验收通过前保持独立可运行，不修改、不移动、不删除（ADR-0001）。
- V2 只读复用项目内固定原始输入（2,000 条菜品 CSV、50 份健康档案 JSON、营养参考文件），但必须独立生成并验证自己的清洗数据、MySQL 初始化数据、RAG 文档和 Qdrant 索引。
- 不整体复制旧项目的 `src`、前端或派生数据；不复制 `.venv`、`node_modules`、模型缓存和运行日志。
- 新旧系统使用不同的 MySQL 数据库、Qdrant Collection、Redis key 前缀和 API 端口（ADR-0001）。
- 每个旧模块在迁移前必须归入 `REUSE`、`REFACTOR`、`REWRITE`、`REMOVE` 或 `PENDING` 之一（ADR-0001）。
- 清理任何旧代码、旧表或旧字段前，必须先通过消费者搜索确认没有在线链路仍在使用。
- 旧项目退出属于单独的受控变更，不在 D4 初始化阶段执行。

## 3. 职责

D4 负责：

1. 定义实现阶段的总顺序和每阶段的前置条件；
2. 汇总全部 12 个模块的迁移分类（来自各模块文档的"迁移分类"小节）；
3. 定义新旧系统的隔离规则和命名空间；
4. 定义数据迁移策略——什么可以复用、什么必须重建；
5. 定义清理清单——每项清理内容的前置确认步骤；
6. 定义旧项目退出条件——全部满足后才能删除旧项目；
7. 定义迁移回滚策略——如果 V2 验收失败怎么办。

## 4. 非职责

D4 不负责：

- 编写迁移脚本或自动化工具；
- 执行数据迁移或数据库初始化；
- 审查旧代码的实现细节（各模块在自己的详设中完成旧实现审查）；
- 管理 Git 分支、合并策略或发布流程（属于工程实践）；
- 决定旧项目归档后的物理存储位置。

## 5. 实现顺序

与文档建设顺序一致，迁移实现分四个阶段：

### 阶段 1：数据与确定性能力（B1-B6）

```
B1 数据工程 → B3 菜品食材 → B2 用户健康档案 → B4 健康规则引擎 → B5 时间步骤 → B6 营养评分
```

前置条件：全部阶段 B 模块文档 APPROVED。

阶段 1 完成标志：
- 所有离线构建流水线通过 B1 质量门禁
- MySQL 固定业务数据表初始化成功
- Qdrant 菜品检索索引构建成功
- `rebuild_all()` 无错误完成
- B4 离线覆盖审核全部 `complete`

### 阶段 2：检索、规划与工作流（C1-C4）

```
C1 RAG 检索 → C2 菜单规划 → C3 Agent 工作流 → C4 上下文记忆
```

前置条件：阶段 1 完成 + 全部阶段 C 模块文档 APPROVED。

阶段 2 完成标志：
- C1 混合检索链路完整可用
- C2 菜单规划生成 3-5 个差异方案
- C3 全部节点和转换函数可运行
- C4 会话创建、恢复和投影可用

### 阶段 3：交付与前端（D1-D2）

```
D1 API 与 SSE → D2 回答与前端
```

前置条件：阶段 2 完成 + 全部阶段 D 模块文档 APPROVED。

阶段 3 完成标志：
- POST/GET/SSE/Cancel 全部端点可用
- 前端 SSE 状态机完整
- 前端禁止字段过滤生效

### 阶段 4：全链路验收与清理（D3-D4）

```
D3 测试与验收 → D4 迁移与清理
```

前置条件：阶段 3 完成 + D3 全部验收条件通过。

阶段 4 完成标志：
- D3 §12 的 11 条验收条件全部通过
- 新旧关键场景对照完成
- 旧项目退出审查通过

## 7. 新旧系统隔离规则

### 7.1 运行时隔离

| 资源 | 旧系统（program） | 新系统（program_v2） |
|---|---|---|
| MySQL 数据库 | `food_agent` | `food_agent_v2` |
| Qdrant Collection | `recipe_retrieval` | `recipe_retrieval_v2` |
| Redis key 前缀 | `session:` / `request:` | `v2:session:` / `v2:request:` |
| API 端口 | 8000 | 8001 |
| 前端端口 | 5173 | 5174 |
| Docker Compose 项目名 | `food-agent` | `food-agent-v2` |

### 7.2 数据隔离

- V2 固定原始输入从旧项目只读复用（同一份 CSV/JSON 文件），但所有派生产物独立生成；
- V2 不得通过导入旧项目的 Python 包来读取清洗后的数据、数据库或索引；
- 新旧系统的运行数据和会话数据完全隔离——不存在跨系统会话迁移；
- 新旧对照测试时允许读取旧系统的 MySQL 数据进行结果比对，但不能在 V2 正式运行链路中依赖旧数据。

### 7.3 代码隔离

- V2 代码只存在于 `program_v2/` 目录；
- V2 不 `import` 旧项目 `program/` 中的任何模块（对照测试可以 import，但不在生产链路中）；
- 新旧系统可以共享 `.model-cache`（BGE 模型文件），因为模型文件只读且内容相同；
- 两套 `pyproject.toml` 各自管理依赖，不共享 `.venv`。

| `fetch_food_composition.py` 及默认流水线中的调用 | B1, B6 | 营养参考固定，不再联网 |
| `UPDATE_PROFILE` 意图/提示词/工作流分支 | B2 | 对话修改档案逻辑移除 |
| 回答提示词中的营养数值/健康标签/疾病描述模板 | D2 | D2 禁止表述规则生效 |
| 前端营养展示组件和 API 类型 | D2 | 前端移除营养分组 |
| 前端健康标签渲染逻辑 | D2 | D2 §9.1 生效 |
| 旧 API 路由中与新端点冲突的路径 | D1 | D1 全部新端点可用 |
| 自动补写缺失步骤的逻辑 | B1, B5 | B5 未知时长保留 `null` |
| 步骤自动补写相关测试 | B1, B5 | 同逻辑移除 |

### 8.3 清理执行规则

- 每一项清理在单独提交中完成，提交消息格式：`cleanup(<scope>): remove <item>`;
- 清理前必须运行全量测试（D3 §11 中的 PR 合并前级别）并通过；
- 如果清理后发现消费者报错，立即回滚该提交；
- 不在同一个提交中混合清理和功能实现。

## 9. 旧项目退出条件

来自 ADR-0001。以下条件全部满足后，才审查归档或删除旧项目 `program/`：

1. 全局不变量全部通过自动验证（D3 §8）；
2. 食材健康硬筛选案例全部通过（正反例，含可选/替代/复合组成）；
3. 五模型工作流及工具权限完整运行（单人+多人各 ≥20 次）；
4. 多人健康交集和多轮上下文场景通过（D3 §7 场景 2+7）；
5. API/SSE/前端完成并通过验收（D3 全部端到端测试）；
6. 新旧关键场景对照完成（V2 结果与 V1 差异有合理解释）；
7. 不存在依赖旧项目的消费者或在途请求；
8. 全部清理项执行完成（D4 §8），旧代码/表/字段/索引已删除。

旧项目退出是一个独立的受控变更，需要单独的架构决策记录，不在 D4 阶段自动执行。

## 10. 迁移回滚策略

如果 V2 在全链路验收中失败且无法在合理时间内修复：

- V1 始终保持独立可运行——它是天然的回滚目标；
- V2 的 MySQL 数据库、Qdrant Collection 和 Redis 数据不删除（保留现场供诊断）；
- 前端和 API 通过切换端口和配置回退到 V1；
- 回滚不涉及代码删除——只涉及运行配置切换。

V2 验收通过、旧项目退出执行后，V1 的归档备份在删除前至少保留 30 天。

## 11. 依赖方向

D4 作为最后一篇模块文档，汇总全部前置模块的迁移结论和清理清单。D4 被 D3 的验收条件引用（D3 §12 条件 11："不存在依赖旧项目的消费者或在途请求"）。D4 不依赖任何尚未完成的模块实现。

## 12. 与全局流程的关系

```
全部 B/C/D 模块的"迁移分类"和"审查后清理项"小节
→ D4 汇总和交叉引用
→ D4 §6 迁移分类总表
→ D4 §8 清理清单（含前置确认步骤）
→ D4 §9 旧项目退出条件
→ 旧项目退出（独立受控变更，非本文执行范围）
```

D4 是 V2 文档体系的最后一篇。它不定义新系统怎么做——前面的 12 篇模块文档已经定义了。D4 定义的是怎么从旧系统到新系统，以及新系统站稳后怎么清理旧系统。
