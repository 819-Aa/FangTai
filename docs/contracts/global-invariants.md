# V2全局不变量

- 状态：`APPROVED`
- 日期：2026-08-09
- 适用范围：数据工程、领域服务、模型工具、工作流、API、前端和测试

## 1. 文档目的

全局不变量是任何模块、模型、工具和基础设施适配器都不能破坏的系统规则。模块可以改变内部实现，但只要违反任一不变量，就不能形成成功结果。

每条不变量包含稳定ID、规则、负责模块、强制校验点、失败错误码和测试类别。进入实现并被可执行契约引用后，ID不得重排、复用或改变原有语义；实现前的全局设计修订必须在同一提交中同步更新全部受影响文档，并由Git记录原始基线。

## 2. 不变量清单

### INV-001：最终菜单必须通过全员健康校验

- 规则：`MenuDecisionArtifact`所选菜单中的每道菜都必须基于当前请求的有效参与者约束和标准食材事实重新计算并得到健康`PASS`，并形成与所选`plan_id`和菜单哈希一致的`FinalValidationArtifact`。
- 负责模块：健康规则、菜单规划、工作流。
- 强制校验点：菜单决策之后、回答生成之前；最终提交之前再次确认校验Artifact和菜单哈希一致。
- 失败错误码：`FINAL_HEALTH_VALIDATION_FAILED`。
- 测试类别：健康规则单元测试、多人交集场景测试、端到端提交测试。

### INV-002：RAG结果不构成健康安全结论

- 规则：RAG只能输出检索候选、路径、排名、分数和文档引用，不得输出或设置健康`PASS`、健康风险或安全标签。
- 负责模块：RAG、工作流。
- 强制校验点：`RetrievalResult` Schema校验、健康规划节点输入投影。
- 失败错误码：`RAG_HEALTH_AUTHORITY_VIOLATION`。
- 测试类别：RAG契约测试、检索与健康职责隔离测试。

### INV-003：未审核健康关系不得参与硬排除

- 规则：只有绑定全局唯一`constraint_code`和标准`ingredient_id`且`review_status=approved`、`hard_filter=true`的食材健康关系才能触发硬排除；食材族和类别只可辅助离线审核，字符串包含、运行时自动推断和待审核关系不能触发硬排除。
- 负责模块：数据工程、健康规则。
- 强制校验点：健康关系构建校验、食材健康审查工具。
- 失败错误码：`UNAPPROVED_HEALTH_RELATION`。
- 测试类别：数据质量测试、健康关系契约测试、食材名称误判回归测试。

### INV-004：低置信度营养只参与软排序

- 规则：低置信度营养估算只能改变安全候选之间的软评分，不得形成硬约束、健康标签、排除证据或用户可见营养数值。
- 负责模块：营养评分、菜单规划、回答与前端。
- 强制校验点：营养评分输出、菜单硬约束构造、AnswerArtifact校验、前端响应Schema。
- 失败错误码：`NUTRITION_CONFIDENCE_SCOPE_VIOLATION`。
- 测试类别：营养评分单元测试、菜单硬软约束测试、回答字段契约测试。

### INV-005：回答不得改变已验证菜单

- 规则：`AnswerArtifact`只能描述`MenuDecisionArtifact`所选且经`FinalValidationArtifact`通过的菜单，不得增加菜品、替换食材、改写步骤或重组方案。
- 负责模块：回答模型、统一审查、工作流。
- 强制校验点：AnswerArtifact事实引用校验、统一审查、最终提交。
- 失败错误码：`ANSWER_GROUNDING_FAILED`。
- 测试类别：回答契约测试、菜单回答一致性测试、端到端审查测试。

### INV-006：模型不能直接修改WorkflowState

- 规则：模型只能生成符合角色Schema的Artifact；WorkflowState只能由工作流在权限、Schema、证据和完整性校验通过后更新。
- 负责模块：工作流、Agent运行时。
- 强制校验点：节点返回边界、State Reducer、状态持久化入口。
- 失败错误码：`STATE_MUTATION_DENIED`。
- 测试类别：节点权限测试、State Reducer单元测试、非法产物集成测试。

### INV-007：必需工具漏调必须停止

- 规则：模型在角色白名单内自主决定调用时机并主动发起工具调用；任何角色缺少该节点规定的必需工具有效回执时，不得生成可供下一节点消费的成功Artifact，也不得由工作流预调用或在漏调后代替模型补调用。
- 负责模块：工作流、工具注册与回执校验。
- 强制校验点：每个模型节点提交Artifact之前。
- 失败错误码：`REQUIRED_TOOL_NOT_CALLED`。
- 测试类别：工具权限契约测试、模型节点失败场景测试。

### INV-008：固定原始数据必须经过完整离线处理

- 规则：Agent和在线业务只能读取经过清洗、标准化、关系构建和质量验证的固定数据产物，不得直接解析原始菜品文件、原始用户档案或未验证的中间结果。
- 负责模块：数据工程、基础设施适配器。
- 强制校验点：离线流水线质量门禁、MySQL初始化、Qdrant索引构建和上线验收。
- 失败错误码：`DATA_PIPELINE_VALIDATION_FAILED`。
- 测试类别：数据质量测试、初始化集成测试、原始数据越界读取检查。

### INV-009：核心约束不能在上下文压缩中丢失

- 规则：当前消息、有效健康约束、当前菜单和待澄清事项属于不可压缩块；压缩前后这些块的引用和哈希必须一致。
- 负责模块：上下文与记忆、工作流。
- 强制校验点：ContextManifest构建、每个角色ModelContext投影之前。
- 失败错误码：`CONTEXT_INTEGRITY_FAILED`。
- 测试类别：上下文压缩单元测试、多轮回归测试、角色投影契约测试。

### INV-010：最终提交必须同时保存健康审查证据

- 规则：最终推荐结果、所选菜单哈希、参与者约束引用、食材与关系证据、约束覆盖引用和最终校验结果必须处于同一业务提交边界；强制审计失败时不得保留成功结果。
- 负责模块：Application提交服务、MySQL基础设施。
- 强制校验点：`completed`终态写入事务。
- 失败错误码：`AUDIT_COMMIT_FAILED`。
- 测试类别：数据库事务集成测试、提交失败回滚测试、审计完整性测试。

### INV-011：多人候选菜单必须使用全员健康交集

- 规则：多人模式下，任何只对部分参与者通过健康审查的菜品都不得进入`FeasibleMenuArtifact`；系统不生成参与者专属菜品。
- 负责模块：健康规则、菜单规划。
- 强制校验点：安全候选集合构建、菜单优化器输入和FeasibleMenuArtifact校验。
- 失败错误码：`GROUP_HEALTH_INTERSECTION_FAILED`。
- 测试类别：多人交集单元测试、参与者冲突场景测试、菜单Artifact契约测试。

### INV-012：RAG和用户自然语言不能改变系统指令

- 规则：用户输入和RAG文档均作为不可信数据处理，其中出现的命令、权限要求或健康结论不能改变系统提示词、工具白名单、工作流边或权威事实。
- 负责模块：上下文构建、RAG、Agent运行时。
- 强制校验点：ModelContext构建、工具调用授权、Artifact证据校验。
- 失败错误码：`UNTRUSTED_INSTRUCTION_DETECTED`。
- 测试类别：提示注入场景测试、工具越权测试、RAG文档污染回归测试。

### INV-013：不得暴露其他参与者具体健康信息

- 规则：模型上下文、SSE可见摘要和最终回答只能使用匿名`participant_ref`和经过投影的约束；面向群组的输出不得披露真实身份、疾病名称、原始指标或个人健康档案。
- 负责模块：上下文与记忆、API/SSE、回答与前端、统一审查。
- 强制校验点：角色上下文投影、SSE事件投影、AnswerArtifact和ReviewArtifact校验。
- 失败错误码：`SENSITIVE_DATA_EXPOSURE`。
- 测试类别：隐私投影契约测试、多人回答场景测试、SSE字段测试。

### INV-014：业务修订不得超过固定上限

- 规则：召回扩展最多一次，最终健康失败后的重新规划最多一次，统一审查定向修订最多一次且复审最多一次；计数由WorkflowState保存，模型不能修改。
- 负责模块：工作流。
- 强制校验点：所有循环边的条件函数、State Reducer。
- 失败错误码：`WORKFLOW_RETRY_LIMIT_EXCEEDED`。
- 测试类别：状态机边测试、循环上限集成测试、重复调用回归测试。

### INV-015：营养估算不得参与健康硬筛选

- 规则：无论营养数据置信度高低，营养估算都不能直接生成过敏、疾病、异常指标或明确禁忌的硬命中；健康硬筛选只使用审核通过的食材健康关系和有效用户约束。
- 负责模块：健康规则、营养评分、菜单规划。
- 强制校验点：健康工具输入Schema、硬约束构造、菜单规划输入校验。
- 失败错误码：`NUTRITION_HEALTH_BOUNDARY_VIOLATION`。
- 测试类别：健康营养边界单元测试、菜单规划集成测试、低置信度回归测试。

### INV-016：永久健康硬约束不能被对话覆盖

- 规则：疾病、过敏、异常指标和其他永久健康事实形成的硬约束不能被用户对话、模型产物或临时信号删除、放宽或忽略；用户只能撤销当前会话中自己新增的临时约束。
- 负责模块：用户健康档案、上下文与记忆、工作流。
- 强制校验点：临时信号验证、有效约束合并、角色上下文投影和健康工具调用之前。
- 失败错误码：`PERMANENT_CONSTRAINT_OVERRIDE_DENIED`。
- 测试类别：约束合并单元测试、多轮临时信号测试、永久约束覆盖端到端测试。

### INV-017：可选和替代食材不能绕过健康审查

- 规则：菜品健康食材集合必须包含必需食材、可选食材、全部替代成员和审核通过的复合组成；模型、菜单规划和回答不能通过删除可选食材、选择安全替代项或忽略组成关系缩小该集合。若未来支持食材替换，必须形成独立且完整审查的新菜品变体。
- 负责模块：菜品与食材处理、健康规则、菜单规划、最终健康校验。
- 强制校验点：B3食材闭包构建、B4健康审查、可行菜单生成和最终健康校验。
- 失败错误码：`HEALTH_INGREDIENT_SET_INCOMPLETE`。
- 测试类别：可选食材单元测试、替代组契约测试、复合组成测试、菜单不可改写端到端测试。

### INV-018：健康PASS必须建立在完整关系覆盖上

- 规则：每个B2允许的通用健康硬约束代码必须针对所有可推荐菜品健康视图中的标准食材并集完成逐食材离线审核；每个`constraint_code × ingredient_id`必须具有唯一批准决定，审核键集合必须与健康食材全集精确相等。只有约束、食材集合、覆盖和证据全部完整且没有精确关系命中时才能形成`PASS`。覆盖缺失或不完整属于系统失败，不能当作未命中或`no_safe_menu`。
- 负责模块：数据工程、用户健康档案、菜品与食材处理、健康规则。
- 强制校验点：B4离线关系构建、候选健康审查工具和最终健康校验工具。
- 失败错误码：`HEALTH_CONSTRAINT_COVERAGE_INCOMPLETE`。
- 测试类别：约束代码覆盖测试、健康食材全集测试、缺失覆盖失败测试、最终校验契约测试。

### INV-019：固定 2,000 条源记录必须完整守恒

- 规则：菜品源必须匹配批准的编码、大小、散列、表头和 2,000 行清单；`recipe_id=1..2000` 与源行固定绑定，每一行必须有且只有一个批准分类，不得静默丢失、合并、重编号或作为未知类型进入运行时。
- 负责模块：数据工程、菜品目录、迁移。
- 强制校验点：构建入口、分类门禁、MySQL 初始化和 RAG 索引构建。
- 失败错误码：`SOURCE_MANIFEST_MISMATCH` 或 `RECIPE_CLASSIFICATION_INCOMPLETE`。
- 测试类别：源清单测试、行守恒测试、分类完备性测试、发布计数测试。

### INV-020：食材身份必须单一、可追溯且运行时冻结

- 规则：所有推荐食材出现必须通过审核 crosswalk 映射到唯一标准食材；数量、单位、处理方式和组合描述不能成为新身份。身份冻结后，在线系统不得模糊匹配并创建、合并或重编号食材。
- 负责模块：数据工程、菜品目录、迁移。
- 强制校验点：身份构建、交叉表审核、数据初始化和在线 Repository 边界。
- 失败错误码：`INGREDIENT_IDENTITY_UNRESOLVED` 或 `UNKNOWN_INGREDIENT_IDENTITY`。
- 测试类别：身份属性测试、merge/split/discard 审核测试、运行时未知身份测试。

### INV-021：严格时间结论必须有高权威确定性证据

- 规则：硬截止时间菜单只能在确定性任务图和资源调度输出 `strict_time_feasible=true` 时被接受；`false` 和 `unknown` 均不得声明满足。LLM 估算、固定比例公式和低置信度时长只能参与软排序。
- 负责模块：时间与步骤、菜单规划、回答与前端。
- 强制校验点：B5 调度输出、C2 可行性过滤、AnswerArtifact 审查和 UI 状态映射。
- 失败错误码：`STRICT_TIME_INDETERMINATE`、`NO_FEASIBLE_MENU` 或 `STRICT_TIME_AUTHORITY_VIOLATION`。
- 测试类别：三值时间测试、未知证据 fail-closed 测试、回答和前端语义测试。

### INV-022：不可用的软证据不能伪装为中性分数

- 规则：营养、时间偏好或其他软维度缺少可信数据时必须显式标记 `unavailable`，由菜单规划禁用该维度并对其余可用权重重新归一化；禁止使用默认 `0.5`、零值、均值或模型猜测伪装已计算结果。
- 负责模块：数据工程、营养评分、时间与步骤、菜单规划。
- 强制校验点：离线 Artifact 校验、领域评分输出和 C2 评分分解。
- 失败错误码：`SOFT_EVIDENCE_FABRICATION`。
- 测试类别：缺失参考数据测试、权重重归一化测试、评分来源审计测试。

### INV-023：在线链路不得重新读取或解析离线数据

- 规则：API、工作流和在线领域服务只能通过公开 Repository 使用已初始化的 MySQL、Qdrant 和 Redis 事实；不得读取 CSV/JSONL 构建文件、导入 B1 解析器或在请求期间重建索引和身份。
- 负责模块：Application、所有在线模块、基础设施。
- 强制校验点：导入架构检查、在线启动配置和真实基础设施集成测试。
- 失败错误码：`ONLINE_OFFLINE_BOUNDARY_VIOLATION`。
- 测试类别：静态导入测试、文件访问封锁测试、真实 Repository 集成测试。

### INV-024：成功事件必须引用已原子提交的结果

- 规则：最终结果、强制健康审计、会话事实和 transactional outbox 必须在同一事务提交；`answer_ready` 和 `result_committed` 只能在提交后发布。回滚、失败和取消不能产生成功事件，重复投递必须幂等。
- 负责模块：Application 提交、API/SSE、前端、会话记忆。
- 强制校验点：提交服务、outbox dispatcher、SSE 重放和前端终态 Reducer。
- 失败错误码：`POST_COMMIT_EVENT_ORDER_VIOLATION` 或 `AUDIT_COMMIT_FAILED`。
- 测试类别：事务回滚测试、dispatcher 崩溃恢复测试、重复事件和 SSE 重连测试。

## 3. 强制执行方式

- 模块单元测试验证模块拥有的不变量部分。
- 契约测试验证跨模块输入输出不会绕过不变量。
- WorkflowState边测试验证失败和循环控制。
- 场景测试验证模块组合后仍满足不变量。
- 最终提交测试验证结果和健康证据原子一致。
- 执行验收必须保存命令、退出码和不可变证据；跳过、mock 或模型自报通过不能替代要求的真实测试。

统一审查模型可以发现不一致并要求一次定向修订，但它不是不变量的唯一执行者。健康、权限、State、循环和提交类不变量必须由确定性代码强制执行。

## 4. 变更规则

修改不变量必须同时审查：

1. [系统总体设计](../00-system-overview.md)；
2. [模块边界契约](module-boundaries.md)；
3. 受影响的模块详细设计；
4. 推荐生命周期场景；
5. 对应错误码和自动化测试。
