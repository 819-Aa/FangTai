# DeepSeek V4 Flash 整改执行契约

- 状态：`APPROVED`
- 日期：2026-08-09
- 适用范围：使用 DeepSeek V4 Flash 执行 V2 整改计划的每一个任务

## 1. 目标

无法、也不需要约束模型内部如何思考；本契约约束的是它能修改什么、必须提交什么证据、何时可以进入下一阶段，以及什么结果会被拒绝。DeepSeek 可以在任务允许的局部实现范围内选择代码组织和等价算法，但不能自由改变需求、契约、数据口径、安全语义或验收标准。

## 2. 权威顺序

发生冲突时按以下顺序处理，低层不得覆盖高层：

1. 用户已确认的书面决定和 ADR；
2. `docs/contracts/` 与全局不变量；
3. 模块详细设计和端到端场景；
4. 批准的整改执行计划；
5. 当前实现和旧 `program`；
6. 模型自己的推断、偏好和临时优化。

发现冲突时必须停止并形成 `BLOCKED_SPEC_CONFLICT`，不得自行挑选更容易实现的一方。

## 3. 外部任务信封

每个任务开始前由执行控制者提供不可变 `TaskEnvelope`：

```yaml
task_id: Txx
spec_hash: sha256
base_commit: git_sha
allowed_paths: []
forbidden_paths: []
required_tests: []
required_invariants: []
required_artifacts: []
human_gates: []
stop_conditions: []
```

- DeepSeek 不能修改任务信封、批准文档、基线测试或验收脚本。
- 写入只能发生在 `allowed_paths`；任何越界 diff 立即拒绝本任务。
- 若合法 Git `base_commit` 不存在，返回 `BLOCKED_GIT_METADATA`。禁止 `git init`、覆盖 `.git`、制造伪基线或在未知基线上继续。

## 4. 每任务七步闭环

DeepSeek 每个任务必须按顺序提交：

1. **重述契约**：列出输入、输出、不变量、明确非目标和未知项；
2. **先写失败测试**：证明测试在实现前因目标缺失而失败，并保存退出码；
3. **最小实现**：只修改白名单文件，不顺手重构相邻模块；
4. **局部验证**：运行任务指定测试、静态检查和契约检查；
5. **全局校准**：运行受影响的不变量、上下游契约和规定回归；
6. **自审 diff**：按文件解释修改，列出风险、假设和未解决项；
7. **独立验收**：由新上下文只读审查代码与机器证据；通过后外部控制者才解锁下一任务。

缺少任何一步，任务状态只能是 `rejected` 或 `blocked`，不能是 `passed`。

## 5. 可接受的自由度

在不改变公开 Schema、确定性语义、复杂度上限和验收证据的前提下，DeepSeek 可以选择：

- 私有函数拆分、命名和局部数据结构；
- 等价的解析或调度实现；
- 测试夹具的组织方式；
- 小范围消除重复和可读性改进。

以下事项没有自由裁量权：

- 固定源清单、2,000 条身份和分类闭合；
- 食材 ID 重建、健康关系人工批准与 fail-closed；
- B1 唯一解析边界及在线禁止读离线文件；
- 预计单值时间布尔语义和营养 all-or-nothing 不可用语义；
- 五模型职责、必需工具、Artifact 权限和失败原则；
- 最终健康复核、事务 outbox 和前端完成语义；
- 测试期望、质量阈值和安全不变量。

## 6. 证据包

每任务必须生成只读验收包，至少包含：

```text
task-envelope.yaml
spec-hash.txt
changed-files.txt
diff.patch
red-test.json
verification.json
commands/<n>.stdout
commands/<n>.stderr
review.json
```

`verification.json` 对每条命令记录命令文本、工作目录、开始/结束时间、退出码和输出文件 SHA-256。模型自己写“测试通过”不算证据；验收器必须重新运行关键命令并核对 diff。

## 7. 强制停机条件

遇到以下任一情况必须停止，不能继续尝试规避：

- 源文件散列、行数、编码或表头不匹配；
- Git 元数据无效、基线不明或工作区出现无法归属的重叠修改；
- 需要新增/删除菜品、动态创建食材身份或改变已确认 ADR；
- 需要替人批准食材健康关系或作出医疗判断；
- 需要执行未授权的删除、覆盖、生产写入或外部发布；
- P0 不变量失败、验收脚本被修改、测试仅因跳过而“通过”；
- 文档、Schema、实现或消费者之间出现无法按权威顺序消解的冲突。

模型应返回准确的 `BLOCKED_*` 状态、证据和最小待决问题，不得提供伪造兜底。

## 8. 阶段闸门

每阶段只有外部控制者可以从 `locked` 改为 `unlocked`：

```text
S0 基线与Git -> S1 契约测试 -> S2 固定数据重建 -> S3 B2/B3/B4
-> S4 B5/B6/C1 -> S5 C2/C3/C4 -> S6 API/Application/Frontend
-> S7 全链路验收
```

阶段通过需要：本阶段所有任务验收包完整、P0 为零、锁定测试未修改、独立审查通过和工作区 diff 可归属。DeepSeek 的文字声明不能解锁阶段。

## 9. 人工闸门

以下决定必须由人完成并以签名清单进入构建：

- 2,000 条记录分类的争议项；
- 食材 merge/split/discard 的争议项；
- 全部 `constraint_code × ingredient_id` 的健康关系批准；
- 任何对 ADR、固定数据清单、健康语义和最终验收阈值的修改；
- 生产初始化、数据销毁和最终切换授权。

DeepSeek 可以整理候选、差异和证据，但不能把自己的输出标为人工批准。

## 10. 完成定义

只有当计划内全部任务和 S7 验收通过、无未处理 P0/P1、文档与可执行契约一致、前后端真实基础设施全链路成功、失败路径也被证明 fail-closed 时，才可宣称整改完成。单元测试通过、mock E2E、前端能构建或模型能生成回答都不等于全链路完成。
