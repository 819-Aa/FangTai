# 方太个性化健康膳食推荐 Agent：面试问题与参考回答

本文档用于项目面试准备，内容以当前版本的实际实现为准。回答时需要始终把握一条主线：**千问负责理解自然语言，确定性程序负责检索、健康审核、菜单规划、状态变更和最终提交。**

## 一、项目开场

### 1. 请介绍一下这个项目

**参考回答：**

这是一个面向多人家庭场景的个性化健康膳食推荐 Agent，主要解决普通菜品推荐无法同时处理健康禁忌、多轮菜单调整和结果可追溯的问题。

离线侧，我把原始菜谱映射成标准食材实体，并建立菜谱—食材关系以及健康约束—风险食材关系。在线侧，先由千问把用户自然语言转换成结构化 QueryPlan，再通过 BM25 和 Qdrant 做混合召回，使用 RRF 融合和 BGE 重排。候选菜品需要经过健康审核，菜单规划完成后还会在提交前再次校验。

多轮对话方面，Redis 保存请求状态、临时约束和并发控制，MySQL 持久化当前菜单、历史版本和会话事实，因此可以支持“换掉第二道菜”“不要花生”“恢复上一版”等操作。

这个项目的核心思路是：**让模型处理语义的不确定性，让确定性程序控制健康安全、状态变更和最终结果。**

**继续追问：**

- 为什么不是让大模型直接生成菜单？
- 这个 Agent 和普通推荐系统有什么区别？
- 项目里最难的部分是什么？

**回答雷区：**

- 不要上来罗列技术栈。
- 不要说成“调用大模型推荐几道菜”。
- 不要声称这是医疗诊断系统。

## 二、项目定位与架构

### 2. 这个项目主要解决什么问题？

**参考回答：**

它解决的不是单纯“用户喜欢吃什么”，而是在多人、多种健康限制和连续对话下，如何生成一份安全、可调整、可解释的菜单。

例如一个家庭里可能同时存在高血压、糖尿病、花生过敏和个人忌口。普通语义推荐可能召回看起来合适的菜，但不一定能严格执行这些约束。因此我把健康限制建模为封闭约束，由确定性审核模块控制候选是否可以进入菜单。

**继续追问：**

- 多人健康条件冲突怎么办？
- 健康约束是模型判断的吗？

**回答雷区：**

不要只回答“提高推荐准确率”，这个项目更重要的是**安全约束和多轮状态管理**。

### 3. 为什么要设计成 Agent 工作流？

**参考回答：**

因为请求不是一个简单的输入输出过程，而是包含语义理解、检索、健康审核、菜单规划、状态修改和结果提交等多个阶段。

同时用户会连续修改菜单，例如先生成菜单，再说“第二道菜换掉”“不要牛肉”“恢复上一版”。系统需要识别当前操作、读取已有菜单和历史约束，然后选择对应的执行路径。

因此这里的 Agent 主要体现为**有状态的任务编排**，并不是让多个模型自由讨论。每个节点的输入输出都有结构化契约，健康规则和提交逻辑仍然由程序控制。

**继续追问：**

- 这是不是普通工作流，为什么叫 Agent？
- 有没有使用 LangChain 或 LangGraph？

**回答雷区：**

不要用“多智能体自主决策”包装项目。当前版本更准确的表述是：**模型辅助理解、有状态工作流执行**。

### 4. 为什么不让大模型直接生成最终菜单？

**参考回答：**

直接生成存在三个问题：第一，模型可能遗漏过敏、疾病等硬约束；第二，同一个输入可能生成不同结果，难以测试和复现；第三，模型生成的菜品可能不在当前菜谱库中，无法完成食材审核和数据追踪。

所以我只让模型负责自然语言理解，把结果转换为结构化 QueryPlan。后续检索、健康审核、菜单规划和提交都由确定性程序完成。

**继续追问：**

- 如果模型解析错了怎么办？
- 那大模型在项目中是不是可有可无？

**回答雷区：**

不要说“大模型只负责聊天”。它负责的是关键的**语义边界转换**。

## 三、语义理解与 QueryPlan

### 5. `WORKFLOW_MODE=fast_path` 是什么？

**参考回答：**

`fast_path` 不是绕过模型的规则模式。它会先识别当前操作类型，然后调用千问完成一次语义重写，将用户表达转换成 QueryPlan。后续健康约束合并、检索、审核、规划和提交走确定性链路。

这样既保留了模型理解口语表达的能力，也减少了模型在工作流中反复生成造成的延迟和不确定性。

**继续追问：**

- 为什么只调用一次模型？
- 相比完整模型链路有什么损失？

**回答雷区：**

不能说“fast_path 完全不调用模型”。

### 6. QueryPlan 包含哪些内容？

**参考回答：**

QueryPlan 是用户自然语言和后续执行模块之间的结构化协议，主要包含：

- 餐次、菜品类型、口味、菜系和场景标签；
- 希望包含或排除的食材；
- 营养目标和健康排除条件；
- 菜品数量；
- 时间约束及其软硬属性；
- 语义重写结果、证据引用和输入指纹。

后面的检索和规划模块只消费这些结构化字段，不直接依赖模型生成的自然语言。

**继续追问：**

- 为什么需要输入指纹？
- 为什么时间约束还要区分软硬？

**回答雷区：**

不要只说“就是一个 JSON”，要强调它是**节点之间的执行契约**。

### 7. 大模型输出格式错误怎么办？

**参考回答：**

我做了几层限制：首先使用 Pydantic 对模型结果进行强类型校验，并禁止未定义字段；其次枚举类字段只能从封闭集合中选择；再次检查解析结果是否能从当前消息或上一轮 QueryPlan 中找到依据。

如果模型超时、JSON 不合法或者结果无法通过验证，就回退到确定性解析结果。对于会影响最终菜单但无法安全推断的信息，则进入澄清流程。

**继续追问：**

- 确定性回退是怎么生成的？
- 模型凭空增加一个过敏条件怎么办？

**回答雷区：**

不能说“Prompt 已经保证模型不会出错”。

### 8. 如何避免模型覆盖健康规则？

**参考回答：**

模型输出的只是用户意图和候选条件，没有权限直接修改健康审核结论。

健康审核节点会单独输出带有安全菜品、排除菜品、约束引用和证据引用的 Artifact。菜单规划只能从审核通过的候选集合中选择，最终提交时还会检查健康审核和最终校验结果。

也就是说，模型可以表达建议，但不能覆盖程序产生的健康事实。

**继续追问：**

- 如果模型推荐了审核不通过的菜怎么办？
- Artifact 会不会被后面的节点篡改？

**回答雷区：**

不要把 Prompt 当作系统安全边界。

## 四、菜品检索与重排

### 9. 整个检索链路是怎样的？

**参考回答：**

系统同时执行 BM25 关键词检索和 Qdrant 向量检索，两侧分别召回候选后，通过 RRF 进行排名融合，再使用 BGE Reranker 对候选和用户需求进行精排。

Qdrant 检索时还会结合菜品类型、标签、食材和构建版本等结构化过滤条件。重排后的候选才进入健康审核，而不是直接生成菜单。

**继续追问：**

- 为什么需要三层检索？
- 为什么不直接使用向量相似度？

**回答雷区：**

不要说 Qdrant 负责判断菜品是否健康。

### 10. 为什么采用 BM25 和向量混合检索？

**参考回答：**

BM25 对明确词汇匹配更稳定，比如具体菜名、食材名和菜系；向量检索更适合“清淡一点”“适合夏天”“做起来简单”等语义表达。

两种结果通过 RRF 融合，不需要强行把两边分数校准到同一量纲。然后再使用交叉编码器重排，提高最终候选与完整需求的匹配程度。

**继续追问：**

- RRF 的原理是什么？
- BM25 和向量结果完全不重叠怎么办？

**回答雷区：**

不要只回答“混合检索更加准确”，要能解释两者解决的问题不同。

### 11. 为什么使用 Qdrant？

**参考回答：**

项目需要同时支持向量相似度检索、结构化 Payload 过滤和数据版本隔离，Qdrant 比较适合这一场景。

每个菜品向量不仅包含文本向量，还携带标签、食材、菜品类型和 `build_id` 等元数据，可以在召回阶段排除明显不符合条件的数据。

但 Qdrant 只是召回组件，最终健康结论仍然来自确定性健康审核模块。

**继续追问：**

- 为什么不用 MySQL 做全文检索？
- 为什么不用 Elasticsearch？

**回答雷区：**

不需要贬低其他数据库，说明当前数据规模和项目目标下的选型理由即可。

### 12. RRF 是怎么做融合的？

**参考回答：**

RRF 不直接比较 BM25 分数和向量相似度，而是根据候选在各自结果列表中的排名计算融合分数。

一个菜品如果同时在关键词和向量结果中排名靠前，融合后的排序会更高；只出现在单一路径中的候选也不会被完全丢弃。

它的优势是实现简单，而且不依赖不同检索模型之间的分数归一化。

**继续追问：**

- RRF 的常数怎么选择？
- 为什么融合之后还需要 Reranker？

**回答雷区：**

如果没有实际调参实验，不要编造最优参数和提升百分比。

## 五、食材模型与健康审核

### 13. 为什么要做食材标准化？

**参考回答：**

原始菜谱中的食材名称并不统一，例如“西红柿”和“番茄”、“花生碎”和“花生”可能指向相同或相关实体。如果直接使用字符串匹配，检索、营养计算和健康审核都可能漏判。

因此我先把原始食材映射到标准食材实体，再让菜谱关系、健康风险和检索过滤统一引用标准实体。

**继续追问：**

- 同名但不同加工方式怎么处理？
- 标准化失败的食材怎么办？

**回答雷区：**

不要说只做了字符串去重，这里本质上是实体归一化。

### 14. 菜谱—食材关系模型是怎么设计的？

**参考回答：**

我没有把一道菜简单建模为一组食材，而是区分：

- 必选食材；
- 可选食材；
- 替代选择组；
- 选择组中的默认选项；
- 加工辅料和调味辅料。

这样健康审核时可以判断风险食材是否一定出现，也能判断是否可以通过替换规避风险；菜单展示时也能保留默认做法和可替换信息。

**继续追问：**

- 替代选择组如何审核？
- 可选危险食材是否直接判定整道菜不可用？

**回答雷区：**

不能笼统地说“菜里有风险食材就全部删除”，要结合食材角色。

### 15. 健康约束是怎么建立的？

**参考回答：**

系统将疾病、过敏、异常健康指标和明确忌口转换成封闭的健康约束代码，再通过健康约束—风险食材关系表找到对应风险。

健康审核基于这些结构化关系执行，而不是让大模型判断“某道菜是否适合糖尿病患者”。审核结果还会保留约束来源和命中的食材关系，便于解释和审计。

**继续追问：**

- 疾病约束和过敏约束优先级一样吗？
- 没覆盖到的食材怎么处理？

**回答雷区：**

不要宣称规则库具有临床诊断能力。

### 16. 为什么需要两次健康校验？

**参考回答：**

第一次是在候选召回之后，目的是尽早过滤不安全菜品，保证菜单规划只接收安全候选。

第二次是在最终菜单提交之前，因为菜单规划、替换和恢复历史版本都可能改变菜品组合。最终校验相当于提交前的安全不变量检查，任何一道菜不通过，都不能写入当前菜单。

**继续追问：**

- 两次校验是不是重复计算？
- 如果两次结果不一致怎么办？

**回答雷区：**

不要只回答“为了更安全”，要说明两个检查点保护的是不同阶段。

### 17. 多人健康条件冲突怎么处理？

**参考回答：**

如果生成的是共享菜单，硬约束按照参与者约束的并集执行。例如一个人花生过敏，那么共享菜单中的菜品都不能包含无法规避的花生风险。

审核结果仍然按参与者保留命中证据。如果约束合并后没有可行菜单，系统不会擅自放宽过敏等硬约束，而是返回待澄清问题，例如询问是否拆分个人菜品。

**继续追问：**

- 如果一个人喜欢、另一个人忌口怎么办？
- 什么时候选择澄清，什么时候返回空菜单？

**回答雷区：**

不要为了“必须推荐出结果”而自动放松硬健康条件。

## 六、菜单规划与时间约束

### 18. 菜单规划是怎么做的？

**参考回答：**

菜单规划只从健康审核通过的候选中选择菜品，然后分别处理硬约束和软目标。

硬约束包括菜品数量、健康安全、明确排除食材和必要的时间限制；软目标包括语义相关度、偏好、营养、菜品多样性和历史重复度。

系统会产出多份可行菜单及评分分解，再选出最终方案，而不是让模型直接拼接菜名。

**继续追问：**

- 多样性怎么定义？
- 如果所有目标不能同时满足怎么办？

**回答雷区：**

没有实际实现的评分项不要临场扩展。

### 19. OR-Tools 在项目中做什么？

**参考回答：**

OR-Tools 主要用于烹饪任务的时间可行性计算。

系统把菜品制作过程转换成带依赖关系和资源限制的任务图，例如切配必须在烹饪之前，同一个灶具不能同时被多个任务占用。CP-SAT 计算整体完工时间，用于判断菜单是否满足用户的时间要求。

它不是直接从全部菜品中决定最终菜单，而是负责验证烹饪调度和时间可行性。

**继续追问：**

- 资源冲突怎么表示？
- 为什么不用简单累加每道菜的制作时间？

**回答雷区：**

不要说“OR-Tools 负责推荐菜品”，那会夸大它在主流程中的作用。

## 七、上下文与记忆

### 20. 项目里的上下文是怎么设计的？

**参考回答：**

我将参与者、当前请求、有效健康约束、当前菜单、历史菜单、检索证据和待澄清问题放入统一的 Shared Workflow Context。

同时使用 Context Manifest 记录请求身份、关键数据块哈希、压缩次数和版本信息。每个节点通过结构化 Artifact 读写结果，并校验 `request_id`、数据版本和内容哈希，防止不同请求或不同数据版本的内容被错误拼接。

**继续追问：**

- 为什么普通字典不够？
- 上下文太大怎么办？

**回答雷区：**

不要只讲“把所有内容放进 Prompt”，这个项目的上下文不仅服务于模型，也服务于整个工作流。

### 21. 项目的长期记忆和短期记忆怎么划分？

**参考回答：**

Redis 保存偏运行时的短期状态，包括请求状态、SSE 事件、幂等信息、会话并发锁和当前轮临时约束。

MySQL 保存已经确认的长期事实，包括当前菜单、菜单历史版本、会话事实和健康审核记录。

例如用户说“这顿不要香菜”，可以先作为当前会话的临时约束；菜单成功提交后，菜单版本和必要的会话事实再持久化到 MySQL。这样既方便快速处理当前请求，也能支持恢复上一版。

**继续追问：**

- Redis 数据丢失会怎样？
- 为什么不全部放在 MySQL？
- 用户永久忌口保存在哪里？

**回答雷区：**

不能把 Redis 说成系统的最终事实来源。

### 22. “换掉第二道菜”是怎么执行的？

**参考回答：**

系统先从当前会话读取已提交菜单，通过语义理解识别这是局部替换操作，并定位第二道菜。

然后结合已有健康约束和本轮新增限制召回替代候选，经过健康审核后替换指定位置。新菜单还要通过最终健康校验，成功后作为新版本提交，原菜单保留在历史记录中。

这也是为什么系统必须同时保存当前菜单、历史版本和操作意图。

**继续追问：**

- 如果用户说“换一个清淡点的”怎么办？
- 如果第二道菜不存在怎么办？

**回答雷区：**

不要把它说成简单修改一个数组元素，中间仍需要重新检索和校验。

## 八、一致性、并发与可靠性

### 23. 如何处理重复请求和并发修改？

**参考回答：**

每个请求都有唯一 `request_id`，相同请求和相同输入重复提交时直接返回已有结果；如果同一个请求号对应不同内容，则判定为幂等冲突。

会话修改时使用 Redis 并发锁，并在最终提交中携带 fencing token。MySQL 会拒绝旧 token 的写入，因此即使旧请求执行时间过长，也不能覆盖新请求已经提交的菜单。

**继续追问：**

- 只有 Redis 锁为什么还不够？
- 锁过期后旧请求继续执行怎么办？

**回答雷区：**

不要说“加了分布式锁就绝对不会发生并发问题”。fencing token 才是防止旧执行覆盖新结果的重要保障。

### 24. 为什么需要事务 Outbox？

**参考回答：**

菜单结果写入 MySQL 和事件发布不是同一个存储事务。如果先写数据库再发事件，进程可能在中间崩溃，导致菜单已经提交但前端收不到完成事件。

所以我把菜单结果、审核记录和待发布事件放在同一个 MySQL 事务中提交。后台再从 Outbox 发布事件；失败后可以重新领取和发送，稳定的事件 ID 用于防止重复事件被当成不同事实。

**继续追问：**

- Outbox 能保证 exactly-once 吗？
- 发布成功但状态没更新怎么办？

**回答雷区：**

更准确的说法是：通过稳定事件 ID 和消费幂等实现**业务效果上的去重**，不要轻易宣称严格 exactly-once。

### 25. 如何保证 MySQL 和 Qdrant 使用同一批数据？

**参考回答：**

离线构建时生成 Build Manifest，记录 `build_id`、源数据哈希、Schema 版本、数据行数和内容摘要。

MySQL 固定数据和 Qdrant 向量数据都绑定这个 `build_id`。服务启动和请求执行时检查版本兼容性，检索时也按照当前构建版本过滤，从而避免数据库已经更新但向量索引仍然使用旧数据。

**继续追问：**

- 新版本构建失败怎么办？
- 为什么只校验行数不够？

**回答雷区：**

不要只回答“同时导入两个数据库”，重点是**可验证的数据构建身份**。

### 26. 项目对超时和异常做了哪些处理？

**参考回答：**

当前项目做的是基础可靠性治理，不是完整生产级高可用。

语义理解调用设置了较短超时，超时或格式异常会回退到确定性解析；Qdrant 和外部模型调用也设置了边界超时。系统还支持请求取消、请求幂等、会话并发锁、fencing token、Outbox 失败重放和服务就绪检查。

这些机制主要保证单次请求失败时不会提交错误菜单，同时减少重复执行和部分写入。

**继续追问：**

- 有没有重试？
- 如果 Qdrant 完全不可用怎么办？
- 有没有熔断和限流？

**回答雷区：**

不要说成已经实现完整高可用。当前没有完整的多副本容灾、熔断降级、自动扩缩容和跨区域灾备。

## 九、测试、难点与不足

### 27. 项目是怎么测试的？

**参考回答：**

测试重点不是只验证接口能不能返回，而是验证跨节点不变量。

包括 QueryPlan 契约校验、健康规则测试、检索与重排测试、Artifact 身份绑定、并发锁和 fencing token、事务 Outbox、菜单版本恢复，以及完整多轮场景测试。

项目验收记录中还覆盖了连续生成、局部替换、增加忌口和恢复历史版本等真实操作链路。

**继续追问：**

- 最重要的一条测试是什么？
- 如何测试模型结果不稳定？

**回答雷区：**

如果没有做过在线 A/B 测试，不要编造推荐准确率、点击率或业务提升百分比。

### 28. 项目中最难的部分是什么？

**参考回答：**

最难的不是把各个技术组件连接起来，而是明确模型能力和确定性逻辑之间的边界。

如果完全依赖规则，系统很难理解自然语言；如果让模型控制全部流程，又无法保证健康安全和结果可复现。因此我把模型限制在语义理解阶段，后面的健康判断、状态变更和提交都通过结构化数据和确定性程序执行。

另一个难点是跨节点上下文一致性，所以引入了 Artifact、Context Manifest 和 Build Manifest，分别解决运行时结果、上下文和数据版本的身份问题。

**继续追问：**

- 如果重新设计，你会改变什么？
- 哪一个设计最能体现你的思考？

**回答雷区：**

不要回答“最难的是环境配置、Docker 或者调接口”。

### 29. 这个项目目前有什么不足？

**参考回答：**

目前它仍是一个完整原型，而不是生产级医疗或推荐系统。

主要不足包括：健康知识库覆盖度还需要专业验证；没有真实用户的长期反馈和在线推荐评估；可观测性、限流、熔断、多副本容灾和灾难恢复还不完整；菜谱规模和营养数据质量也还有扩展空间。

如果继续推进，我会优先完善规则知识的人工审核和版本管理，然后建设离线评估集、链路指标和异常降级策略。

**继续追问：**

- 为什么不先增加更多模型？
- 上线前你认为必须补什么？

**回答雷区：**

不要回答“项目已经很完整，没什么不足”。能明确边界通常比强行包装生产级更可信。

### 30. 这个项目最有价值的设计是什么？

**参考回答：**

我认为最有价值的不是某一个模型或者数据库，而是三条边界：

1. 模型负责理解，确定性逻辑负责安全决策；
2. Redis 负责运行状态，MySQL 负责持久事实；
3. 检索结果只是候选，只有经过健康审核和最终校验的菜单才能提交。

这些边界使系统在保留自然语言交互能力的同时，具备可测试、可追踪和可恢复的工程属性。

**继续追问：**

- 如果只能保留一个设计，你保留什么？
- 这些设计是否过度工程化？

**回答雷区：**

不要再次完整背诵技术栈，面试官此时想听的是你的判断和取舍。

## 十、面试统一口径

面试过程中始终保持下面几个说法一致：

- 千问负责**语义理解和 QueryPlan 生成**，不负责最终健康决策。
- `fast_path` 仍然调用模型，但只在语义入口使用一次。
- Qdrant 负责**向量召回和结构化过滤**，不负责健康审核。
- OR-Tools 负责**烹饪任务调度和时间可行性计算**，不要说它直接决定最终菜品。
- Redis 负责运行时状态，MySQL 是已提交菜单和历史事实的持久化来源。
- 健康安全来自确定性约束链和双重校验，不是来自 Prompt。
- 这是具备可靠性设计的完整项目原型，不是生产级医疗诊断系统，也不要包装成完整高可用系统。
- 没有实际测量的数据，不要现场编造准确率、延迟优化比例或业务增长。

## 十一、优先准备顺序

如果面试准备时间有限，优先熟悉以下问题：

1. 项目介绍；
2. 为什么不让大模型直接生成最终菜单；
3. `fast_path` 的实际含义；
4. 混合检索与重排链路；
5. 为什么需要两次健康校验；
6. 上下文如何设计；
7. 长短期记忆如何划分；
8. 如何处理重复请求和并发修改；
9. 项目最难的部分；
10. 项目目前的不足。

这十个问题基本可以覆盖一轮项目深挖面试。
