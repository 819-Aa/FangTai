# Program V2 全链路整改方案（已批准方案基线）

> 状态：`OWNER_APPROVED`
> 日期：2026-08-09
> 适用对象：`program_v2` 设计、实现、数据重建、测试、迁移与 DeepSeek V4 Flash 执行
> 权威边界：本文件已于 2026-08-09 获项目所有者批准，是正式文档修订的方案来源；执行时以 `docs/` 中的 ADR、契约、模块基线和最终整改计划为规范性权威。

正式入口：[V2 文档索引](../docs/README.md)；执行入口：[V2 全链路整改计划](../docs/superpowers/plans/2026-08-09-v2-full-chain-remediation.md)。

## 1. 结论与建议

建议采用“固定事实一次性重建 + 健康链路 fail-closed + Artifact 证据贯穿 + 在线链路按事务终态发布”的方案，不建议在现有实现上逐个修补症状。

V2 开发文档的架构方向不需要推翻。当前主要问题是实现没有真正落地文档规定的数据权威、模块边界、失败语义和证据要求。整改应以 V2 文档为主准则，`program` 只借鉴已经被真实数据验证过的解析案例、测试方法和工程边界；任何与 V2 不变量冲突的 V1 逻辑不得迁入。

本方案已经选定以下总体策略：

1. 菜品原始数据永久固定为 2,000 行，不做增量、追加、删除或在线版本切换；
2. 原始 CSV 永远只读，`recipe_id=1..2000` 永久绑定原始行位置；
3. 当前 V2 的 3,326 个食材 ID 不具备保留价值，执行一次完整重建并生成旧→新审计映射；
4. 2,000 条原始记录全部进行显式分类，不允许在线猜测记录类型；
5. B1 是唯一离线解析入口，B3/B4/B5/B6/C1 不再重新拆原始食材文本；
6. 健康关系候选可以由程序生成，但 `approved` 和 `complete` 不能由同一算法自动签发；
7. 任何事实、覆盖、证据或范围不完整都进入 `failed`，不得转成 `PASS`、空结果或降级候选；
8. 严格时间与“尽量快”分开：严格时限只接受确定的 `true`，`unknown` 不得声称满足；
9. 营养与模型时间估算只作为软特征；数据不可用时显式禁用该软维度并重新归一化权重，不伪造中性分；
10. 最终回答和 `result_committed` 事件都由成功事务后的持久化事件驱动；
11. DeepSeek V4 Flash 每次只执行一个有边界任务，并在任务内完成实现、自审、复审、回归和证据归档；
12. V1 在 V2 完成全链路验收前保持不动，作为回退系统，不执行提前迁移或删除。

## 2. 已锁定的输入事实

### 2.1 菜品源清单

| 字段 | 固定值 |
|---|---|
| 文件 | `data/raw/recipes_sample_2000.csv` |
| 编码 | `GBK` |
| 字节数 | `1,138,083` |
| SHA-256 | `B2177DC6CDCAE24FC5671C8DADA44295228F4301E3CE620ED11D51B1ABFE4371` |
| 数据行数 | `2,000`（不含表头） |
| 表头 | `名称`、`食材清单`、`烹饪步骤`、`label` |
| ID 规则 | 第 N 条数据行永久对应 `recipe_id=N` |

`program` 与 `program_v2` 当前持有的原始菜品文件哈希一致。后续构建必须先验证上述清单；任一字段不一致立即返回 `SOURCE_MANIFEST_MISMATCH`，不得继续。

### 2.2 明确不做的范围

- 不增加、不删除菜品原始记录；
- 不计算个人份量、人数份量、采购量、`per_serving` 或烹饪营养损耗；
- 不让 Agent 在线解析原始 CSV、原始用户 JSON 或未发布的中间产物；
- 不建设运行时多版本目录、健康规则热切换或蓝绿数据查询；
- 不把 V1 的营养硬阈值、健康风险标签、家庭计量换算和部分可食用菜单语义带入 V2；
- 不让 DeepSeek、运行时模型或关键词程序直接批准医疗健康关系。

## 5. 目标数据链路

```text
固定原始输入
  → SourceManifest 校验
  → RecipeCatalog（全部 2000 条显式分类）
  → IngredientOccurrence / ChoiceGroup / Composition
  → 新 IngredientRegistry + Alias/Family/Category + 旧新 ID 映射
  → B3 各消费者只读视图
  → HealthIngredientUniverse
  → B2 AllowedConstraintCodeRegistry
  → HealthDecisionMatrix（独立人工批准）
  → B5/B6/C1 派生 Artifact
  → 全量门禁通过
  → 空的 V2 MySQL 一次性初始化 + Qdrant 索引初始化
  → 在线 Repository 只读
```

### 5.1 每个正式 Artifact 的共同元数据

所有正式离线产物都应携带或由同目录 Manifest 记录：

- `artifact_type`、`schema_version`、`build_id`；
- 上游 `source_manifest_sha256`；
- 本产物 SHA-256、行数、主键集合哈希；
- 依赖 Artifact 的 ID 和哈希；
- 生成器名称、配置哈希、构建时间；
- `review_status`、审核人/审核批次引用；
- 质量门禁结果和报告引用。

这些字段是离线构建和初始化证据，不引入运行时多版本业务语义。

## 6. 分阶段整改方案

### 阶段 0：执行基线与文档治理

目标：让后续每个修改都可恢复、可审查、不会依据冲突文档执行。

1. 验证 Git 元数据、当前分支和可恢复基线；当前 `.git` 仍不完整时返回 `BLOCKED_GIT_METADATA`，禁止 DeepSeek 自行 `git init` 或覆盖 `.git`；
2. 固化文档权威顺序：全局不变量/模块边界 > 已批准 ADR > 模块文档 > 场景 > 报告/README；
3. 统一端口为 API 8001、前端 5174，清理 8000/5173 漂移；
4. 统一模型配置表述，模型供应商只由环境配置决定，文档不写互相冲突的默认供应商；
5. 将旧“已通过”报告改为历史快照，报告不得作为自动门禁证据；
6. 建立每个任务的 owned files、禁止修改文件、命令和证据目录。

停止条件：没有可恢复基线、权威文档仍冲突或任务边界不明确时，不进入代码修改。

### 阶段 1：B1/B3 固定事实重建

#### 1A. 源与目录

1. 新增 `SourceManifest` 校验器，启动任何构建前验证固定 CSV 的哈希、编码、表头、字节数和 2,000 行；
2. 构建 `RecipeCatalog`，每个 `recipe_id=1..2000` 必须有唯一记录；
3. 对所有记录保存 `record_type`、`variant_group_key/index/count`、身份状态、食材完整性、必需事实状态、推荐资格、原因和来源引用；
4. V1 当前 1,935 dish / 29 preparation / 26 meal_bundle / 8 cooking_program / 2 test 只作为候选审查清单，不作为自动真值；
5. 分类规则输出候选，最终 2,000 条记录必须全部处于显式 `approved` 或明确待审状态；任何待审项阻断正式构建。

#### 1B. 食材注册表一次性重建

1. 从全部食材出现项生成候选，不按出现频率分配 ID；
2. 分开保存标准食材、审核别名、食材族、类别、形态属性、出现级 `consumption_role`、选择组和组成关系；
3. 组标题、数量、单位、准备说明不得进入标准食材名；
4. `ambiguous`、`not_found` 和污染候选进入审查队列，不允许最近词或模型猜测；
5. 审核同义合并、错误拆分和应保留的不同食材，完成后一次性按稳定规则分配新 ID；
6. 输出旧 ID 到新 ID 的 `merge/split/discard` 映射，只用于迁移审计，不参与运行时；
7. 构建 B4、B5、B6、C1 所需的不同消费者视图，消费者不得导入解析内部函数；
8. 可推荐菜品的 B4 视图要求 `unresolved=0`、选择组成员完整、组成状态为 `atomic|complete` 且证据路径完整。

可借鉴 V1：`data_pipeline/catalog.py` 的分组前缀、数量后缀和替代块处理案例，以及 `tests/data_pipeline/test_data_pipeline.py` 的真实数据回归方式。不得借鉴 V1 的健康标签、营养硬限制和群组“部分可食用”逻辑。

#### 1C. 用户档案修复

1. 正确读取 `身高_cm`、`体重_kg`、指标字段单位和孕周期；
2. 以类型化 Schema 保存值、单位、状态和来源引用，缺失保持 `null`；
3. 不按行号覆盖原始用户 ID，显式校验固定 ID 唯一性；
4. `备孕` 等未纳入允许注册表的状态不能静默丢弃，进入业务/健康审核清单；
5. 测试必须比较原始事实和清洗事实，不只检查“字段存在”。

#### 阶段 1 门禁

- 源清单完全一致；
- `recipe_id` 精确等于 `1..2000`；
- 2,000 条记录分类完成，推荐资格可确定；
- 所有合格健康视图零 unresolved、零悬空引用；
- 新食材 ID 唯一稳定，别名和组成无循环；
- 用户档案字段值/单位不发生无解释损失；
- 所有产物先写 staging，全部门禁通过后才允许初始化正式 V2 存储。

### 阶段 2：B2/B4 健康约束与证据重建

#### 2A. B2 约束注册表

1. 建立唯一 `AllowedConstraintCodeRegistry`，B2 只能输出注册代码，未知文本返回澄清或数据错误，不动态拼接代码；
2. 统一疾病事实和异常指标共享代码的规则，合并重复匹配但保留全部 `constraint_id/source_refs`；
3. 明确禁忌必须先经 B3 严格解析成 `ingredient_id`，与 `constraint_code` 严格互斥；
4. 未找到用户档案返回 `HEALTH_PROFILE_NOT_FOUND`，不得返回空约束；
5. 临时信号校验参与者范围、当前消息证据、允许代码、B3 食材身份和作用域；
6. 永久、session、turn 约束按身份键合并；永久约束不可被临时信号撤销或放宽。

#### 2B. 健康决定矩阵

1. 从所有合格 B3 健康视图计算唯一 `HealthIngredientUniverse` 和集合哈希；
2. 程序只生成 `constraint_code × ingredient_id` 候选矩阵，不写 `approved`；
3. 每一对必须得到 `hard_exclude` 或 `no_hard_relation` 的唯一决定；
4. 每个决定保存依据、审核状态、审核批次和证据引用；
5. 健康码没有任何命中也必须保存全量 `no_hard_relation` 决定；
6. 只有独立审核完成后，投影出在线 `health_relations` 和覆盖清单；
7. 集合门禁必须验证：允许代码集合 × 健康食材全集 = 已批准决定键集合；
8. B3 任一食材/组成/资格变化都会使健康全集哈希变化，并强制健康矩阵重新审核。

不可自动化的批准点：关系候选的医学/业务正确性、`备孕` 的约束定位以及边界食材的硬排除决定必须由项目指定的合格审核者确认。DeepSeek 只能准备差异、证据和待审列表，不能替代批准者。

#### 2C. B4 fail-closed 引擎

1. `recipe_ids`、食材视图键集合、参与者集合必须精确一致且非空；
2. 任一菜品不存在、不合格、未解析、组成无效或证据缺失立即失败；
3. 显式禁忌只按已解析 `ingredient_id` 比对；
4. 通用约束只按已批准精确关系比对，运行时禁止名称/类别/营养/模型推断；
5. 回执绑定 `request_id/session_id/participant_scope/retrieval_result_ref/constraint_set_refs/universe_hash/input_hash`；
6. `safe_recipe_ids` 必须是候选集的确定性全员 PASS 交集；
7. 最终校验重新加载 B2/B3 权威事实，校验真实 `menu_hash`，不能接受调用者伪造哈希；
8. `PASS` 回执必须引用覆盖和否定决定证据，而不是生成 `recipe_pass:<id>` 占位符。

#### 阶段 2 门禁

- 每个 B2 允许代码覆盖健康全集；
- 决定矩阵无重复、无缺口、无悬空、无算法自批准；
- 缺食材映射、空参与者、未知码、无证据、错误范围全部稳定失败；
- 多人安全集等于逐参与者 PASS 集的交集；
- 初审与最终校验对相同输入给出相同结果和证据哈希。

### 阶段 3：B5/B6/C1 辅助链路

#### 3A. B5 时间

1. 只读取 B3 步骤和步骤食材绑定视图；
2. 显式精确时间且关键绑定完整才可为 high；
3. LLM 估算标记为 `model_estimate`，最高只参与软排序，模型自报 high 不具备严格时限权威；
4. 无法分类的步骤为 `unknown`，不能默认 `active`；
5. 调度器校验任务图依赖、厨师互斥、设备互斥和被动等待，不使用 40% 等未经文档批准的经验公式；
6. 严格时限请求只接受 `strict_time_feasible=true`；`false` 进入 `no_feasible_menu`，`unknown` 返回 `STRICT_TIME_INDETERMINATE`，不得承诺满足时限；
7. “尽量快”是软偏好，允许使用中低置信度参考排序但不能展示确定分钟。

#### 3B. B6 营养

1. 只读取 B3 `RecipeNutritionInputView`；
2. 修正参考表字段映射（当前参考字段为 `*_per_100g`），使用标准食材和审核别名；
3. 仅用可直接确认的原始数量做菜内相对加权，不扩展到份量/采购量；
4. 未知数量或无参考保持 unknown，不用后一个食材覆盖前一个食材的数值；
5. 按 B2 健康目标生成目标维度评分，实际消费 `goal_weights`；
6. profile 不存在或覆盖为 0 时返回 `unavailable`，C2 将该软维度权重按确定性规则重新归一化；
7. 不返回伪造的 0.5 中性分，不向 B4、回答或前端发送营养数值。

#### 3C. C1 检索

1. RAG 文档只从 B3 合格检索视图构建，不包含不可推荐记录；
2. 建索引前后验证 recipe_id 集合、文档哈希、向量数量和 payload Schema；
3. Qdrant 使用固定镜像版本和独立 staging collection，验收后在服务启动前配置正式 collection；不做运行时热切换；
4. 生产模式向量或 reranker 失败必须返回类型化失败，不回退纯词法；
5. 检索结果绑定 request、query plan、路径和索引构建证据；
6. 多人多路合并保留每个来源路径，扩展查询必须满足差异地板且最多一次；
7. RAG 文本继续作为不可信数据，不能携带工具指令或健康结论进入系统提示。

### 阶段 4：C2/C3 规划、工作流与回答

#### 4A. C2 确定性规划

1. 输入必须是可验证 B4 `HealthEvaluationReceipt`，模型不能直接提交任意安全 ID；
2. 删除安全集为空时回退 RAG 候选的逻辑；
3. 严格执行菜数、必需槽位、槽位上限、锁定/拒绝菜、仅现有食材和去重；
4. 不自适应改变用户明确菜数；不足时返回完整 `no_feasible_menu` 证据；
5. 仅现有食材按 B3 标准 ID 做集合包含，水/盐/食用油使用显式基础调料注册表；
6. 删除随机 shuffle，使用稳定排序、确定性多目标策略和可重复结果；
7. `menu_hash` 由规范化 recipe_id 列表、硬约束、健康回执和算法配置计算；
8. `plan_id` 与内容哈希/请求范围绑定，不按策略名和菜数生成；
9. 3～5 个方案必须真实不同，不能通过同名策略生成碰撞 ID；
10. 替换/恢复产生新计划并重新执行 B4 最终校验。

#### 4B. C3 Artifact 和状态机

1. 为 QueryPlan、HealthEvaluation、FeasibleMenu、MenuDecision、FinalValidation、Answer、Review 建立严格 Schema；
2. 模型输出只进入 Schema 验证，只有确定性 Reducer 可以更新 WorkflowState；
3. 工具回执由运行时生成，保存调用节点、角色、完整参数哈希、结果哈希、范围和证据；
4. 越权调用立即 `TOOL_PERMISSION_DENIED`，不能只把错误文本回给模型后继续；
5. 必需工具必须存在成功且身份匹配的回执；空结果、截断回执和错误路径不能算成功；
6. 菜单决策只能选择 FeasibleMenuArtifact 中的完整方案，禁止拼装；
7. 最终校验回执中的 plan/menu/hash 必须与选择结果完全一致；
8. 未知 Review verdict、缺失 verdict 或 Schema 外值一律失败，不默认 PASS；
9. 回答必须列出结构化 dish refs，并逐项与 B3 公共事实和最终菜单校验；
10. `audit_answer_text` 和敏感内容审计在发布前确定性执行，统一审查模型是补充，不是唯一防线；
11. 召回扩展、健康重规划、回答修订和复审使用 WorkflowState 统一计数并覆盖所有循环边。

### 阶段 5：C4/D1/D2、数据库、SSE 与前端

#### 5A. C4 会话

1. 创建/恢复会话时校验参与者映射，不能用新请求静默改写已有会话身份；
2. 先合并 B2 永久与临时约束，再创建不可变 ContextManifest；
3. 每个模型节点投影前复核 Manifest；约束合法更新后生成新的 Manifest，不绕过校验；
4. Redis 完整保存参与者映射、当前菜单、菜单历史、待澄清、临时约束、事件详情和压缩审计；
5. session/turn 约束按生命周期持久化与清理；
6. 菜单只有最终事务成功后才进入 current_menu/history；
7. 使用带 owner token 和续租/安全释放的会话锁；生产环境 Redis 不可用时不得放行并发写；
8. `get_current_menu`、session API、取消和恢复使用真实状态，不返回固定占位符。

#### 5B. 数据库与原子提交

1. 固定业务表按正式文档补齐 RecipeCatalog、Occurrence、Alias、ChoiceGroup、Composition、ConstraintRegistry、HealthDecision、Coverage 等结构；
2. 数据初始化要求空的 V2 目标库或明确批准的一次性重建，禁止逐表 commit 和无条件 upsert；
3. 全部初始化数据在一个受控事务中写入并验证精确计数/FK/哈希，失败整体回滚；
4. 最终推荐事务保存真实 menu_hash、参与者约束引用、食材路径、关系决定、覆盖引用、最终校验和回答哈希；
5. request_id 幂等：重复提交不增加 session request_count、不新增 menu_version、不重复事件；
6. 同一事务写入 SSE outbox，事务成功后由 dispatcher 依次发布 `answer_ready`、`result_committed`；
7. 提交失败只产生 failed/error，不会先发布成功事件；
8. V1 数据库、Collection 和 Redis namespace 全程保持不变。

#### 5C. D1/D2/API/SSE

1. POST Schema 强制验证 participant_ref、user_id、类型、数量、消息长度和 session 归属；
2. `/v1/users` 改成最小选择目录，不返回过敏、疾病、特殊状态、原始 user_id 或健康详情；
3. `analysis_ready` 先扫描 payload，再发送原 payload，不能把违规列表当 payload；
4. 回答文本执行内容审计，不只扫描 JSON 字段名；
5. 修复 SSE 闭包变量 F823、Last-Event-ID 精确续传、重复事件、终态关闭和断线恢复；
6. 所有业务终态均有明确事件和状态，不把 `no_safe_menu/no_feasible_menu/needs_clarification` 当普通空答案；
7. 健康端点分别报告进程存活与 MySQL/Redis/Qdrant/模型就绪，不以固定 `ok` 掩盖依赖故障。

#### 5D. 前端

1. UI 只显示匿名“参与者 A/B”，不显示用户编号、过敏、疾病或特殊人群；
2. 首次请求保存 session_id，后续轮次复用同一 session；
3. 实现澄清问题、取消、no-safe/no-feasible、failed/interrupted 和重试入口；
4. EventSource 断开按 Last-Event-ID 恢复，轮询只是状态确认，不创建新请求；
5. answer_ready 只展示已审计内容，result_committed 后才标记完成；事务失败时不能保留“完成”状态；
6. 前端对禁止字段做兜底过滤，并为状态机、隐私和 SSE 恢复编写自动测试；
7. 更新过期 README，统一端口和启动方式。

### 阶段 6：验收与迁移

1. 单元测试覆盖每个解析规则、Schema 和状态转换；
2. 契约测试覆盖所有公开端口和禁止依赖；
3. 18 条不变量每条至少有一个负向测试和一个组合/场景证据；
4. MySQL、Redis、Qdrant 不可用时，正式集成套件必须失败，不允许 skip 后宣布通过；
5. 付费 LLM 测试与确定性验收分开，模型不稳定不能掩盖基础链路错误；
6. 建立真实 FastAPI + SSE + MySQL + Redis + Qdrant 的端到端测试，而不是只收集 0 条用例的文件；
7. 以固定对话用例覆盖单人、多人冲突、严格时间、仅现有食材、临时健康信号、澄清、替换/恢复、取消、断线续传和提交失败；
8. Ruff 零错误、后端全套通过、前端 build 与测试通过、数据门禁通过后才生成候选发布报告；
9. V2 与 V1 并行对照，V2 未通过 P0/P1 验收前不替换 V1；
10. 迁移后再执行旧代码清理，清理任务与功能修复分开审批。

## 7. DeepSeek V4 Flash 强制执行协议

批准本方案后，应把本节拆成正式执行契约和逐任务计划。DeepSeek 每次任务必须严格遵守下列状态机。

### 7.1 单任务上下文

每个执行上下文只能有一个任务 ID，例如 `DATA-03` 或 `HLT-03`，并明确：

- 目标和对应不变量；
- 前置条件及上游 Artifact 哈希；
- 允许修改文件；
- 禁止修改文件；
- 必须先出现的红色测试；
- 实现后的目标测试、回归测试和数据门禁；
- 输出证据文件；
- 停止条件和回滚点。

不得在一个上下文中同时“顺便修”其他模块。发现旁路问题只记录到 backlog，不扩展当前任务权限。

### 7.2 每任务七步循环

1. **Read**：重新读取当前任务涉及的正式文档、Artifact Schema 和已有代码；
2. **Preflight**：验证 Git/备份、上游门禁、固定输入哈希和工作区差异；
3. **Red**：先写能稳定复现缺口的测试，记录预期失败码；
4. **Implement**：只做满足任务的最小实现，不修改测试来适配错误行为；
5. **Verify**：运行任务测试、相关模块回归、对应不变量负向测试和静态检查；
6. **Audit**：按“规范一致性、数据完整性、权限/隐私、失败语义、回归风险”五个角度自审；
7. **Calibrate**：在一个新的审查上下文中只看需求、diff、测试和证据；若审查失败，回到 Implement，直至通过或阻塞。

任务只有在 Implementer 证据和独立 Reviewer 证据均为 PASS 时才可进入下一任务。

### 7.3 禁止行为

DeepSeek 不得：

- 自动批准健康关系或把关键词命中写成 `approved`；
- 遇到缺数据时返回空集合、默认值、旧候选或 PASS；
- 修改/删除/跳过失败测试以获得绿色结果；
- 把外部依赖不可用的 skip 计为全链路通过；
- 在 B3/B4/B5/B6/C1 中重新解析原始 CSV 或原始用户文件；
- 让模型输出覆盖确定性事实、权限、状态或提交结果；
- 捕获广泛异常后静默降级；
- 用手写“passed”计数代替命令生成证据；
- 在未授权任务中修改正式文档、基础设施密码、V1 或 `.git`；
- 使用 `latest` 镜像、无锁依赖或不可复现模型版本；
- 在 P0、Schema、数据哈希或不变量测试失败时继续下一个阶段。

### 7.4 每任务证据包

每个任务生成机器可读证据，至少包括：

```json
{
  "task_id": "HLT-03",
  "invariants": ["INV-001", "INV-018"],
  "precondition_hashes": {},
  "changed_files": [],
  "red_test": {"command": "", "expected_failure": ""},
  "verification": [{"command": "", "exit_code": 0, "report_ref": ""}],
  "artifact_hashes": {},
  "implementer_verdict": "PASS|FAIL|BLOCKED",
  "reviewer_verdict": "PASS|FAIL|BLOCKED",
  "open_risks": [],
  "next_task_allowed": false
}
```

`next_task_allowed` 只能由确定性门禁根据两个 PASS 和全部必需命令 exit code 计算，不能由模型自由填写。

### 7.5 强制停止条件

出现以下任一情况立即停止并报告项目所有者：

- 源文件清单不一致；
- Git/备份基线不可恢复；
- 需要确定医疗健康关系、`备孕` 等业务语义或记录分类边界但没有批准者；
- 需要删除/重建现有 V2 数据库卷、Collection 或其他有状态资源，且没有精确目标和授权；
- 正式文档彼此冲突且会改变行为；
- P0 负向测试仍可通过错误路径；
- 需要访问未提供的凭据、外部服务或付费模型；
- 修改范围将触及 V1、用户数据或任务外文件。

## 9. 最终验收条件

只有同时满足以下条件，才能把 V2 标为 `READY_FOR_REPLACEMENT_REVIEW`：

1. 固定菜品 SourceManifest 精确通过；
2. 2,000 条 RecipeCatalog 全部分类并有资格决定；
3. 新 IngredientRegistry、别名、出现、选择组和组成零悬空、零污染身份；
4. 所有合格菜品健康视图零 unresolved；
5. B2 允许码与 B4 已批准决定矩阵集合精确相等；
6. 所有健康决定由独立审核确认，算法没有自批准；
7. B4 所有缺失/错配/越界负向测试稳定 failed；
8. C2 任何方案都是 B4 安全集子集且满足全部硬约束；
9. 所有 Artifact、回执、plan/menu hash 和最终提交身份一致；
10. 回答事实完全来自最终菜单，文本通过隐私和禁止内容审计；
11. MySQL 事务失败不会发布成功事件，重复请求无重复副作用；
12. 多轮会话、临时约束、菜单历史、锁、取消和 SSE 续传通过集成测试；
13. 前端不显示用户 ID、过敏、疾病、特殊人群或内部营养值；
14. INV-001～INV-018 均有可执行正/负证据；
15. 后端、前端、数据门禁、Ruff、真实 E2E 全部通过且无必需 skip；
16. V1 未被修改，回退路径已验证；
17. 审查报告中的所有 P0/P1 已关闭，遗留 P2 有明确接受人和期限。

`READY_FOR_REPLACEMENT_REVIEW` 仍只是进入替换评审，不等于自动切换生产系统。
